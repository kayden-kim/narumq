# 문서 작성 규칙

이 파일은 `docs/` 전체에 적용한다. 하위 `AGENTS.md`는 유형별 규칙을 추가한다. 같은 범위의 규칙이 충돌하면 더 가까운 지침을 따른다. 사용자 지시는 저장소 지침보다 우선한다.

[용어집](#용어집) 규칙은 저장소 전체의 `GLOSSARY.md`·`GLOSSARY-MAP.md`에 적용한다.

## 문서 배치

| 디렉터리·파일 | 포함할 내용 | 포함하지 않을 내용 |
| --- | --- | --- |
| `requirements/` | 문제, 목표, 범위, 제약, 우선순위, 수용 기준 | 구현 선택, 상세 형식, how-to 절차 |
| `specs/` | 외부 동작, 상태 전이, 오류, 통신 절차, 화면 흐름·화면 상태·입력 검증과 텍스트 와이어프레임 | 선택의 역사, 장문의 배경, 모듈 내부 구조, 시각 디자인 원본의 복제 |
| `design/` | 디자인 시스템(`DESIGN.md`)의 토큰·시각 원칙·참고 자료, 화면 스펙별 HTML 시안(`design/mockups/`) | 화면 동작·상태·수용 테스트, 코드에 스타일을 적용하는 규칙 |
| `contracts/` | 데이터를 만드는 쪽과 사용하는 쪽, 교환 형식, 버전, 호환성 | 제품 배경, 전체 상태 전이, 운영 절차 |
| `architectures/` | 코드 지도(구성요소별 코드 위치·진입점·핵심 흐름), 모듈 설계(모듈 내부 구조·데이터 모델·처리 순서·초기화 시점), 의존 관계, 권한 확인이 필요한 경계 | 선택의 역사, 정확한 교환 형식, 외부 동작 정의, 화면 배치, how-to 절차 |
| `decisions/` | 배경, 결정, 대안, 결과, 재검토 조건 | 요구사항 복제, 사용 안내 |
| `explainers/` | 개념, 원리, 아키텍처 문서를 따라 실제 코드를 읽는 방법, 선택의 장단점 | 필수 동작이나 금지 사항, 코드 구조의 기준 정의, 작업 절차 |
| `conventions/` | 이름 짓기, 소스·테스트·서식 규칙과 준수 확인 방법 | 제품 동작, 구조 결정, 운영 절차 |
| `how-to/` | 전제 조건, 단계, 검증, 복구 | 결정 근거의 반복 설명 |
| `incidents/` | 발생한 사고의 영향, 시간순 경과, 확인된 원인·가설, 대응·복구 결과, 후속 조치와 증거 | 새 요구사항·설계의 기준 정의, 반복할 운영 절차, 근거 없는 원인 단정 |
| `templates/` | 문서 작성을 시작할 때 복제하는 템플릿 원본 | 작성한 프로젝트 문서, 채택된 구현 기준, README 문서 목록 |
| `GLOSSARY.md`·`GLOSSARY-MAP.md`(저장소 루트 또는 맥락 폴더) | 업무 용어의 이름, 한두 문장 정의, 쓰지 않을 표현, 맥락 목록과 맥락 사이의 관계 | 요구사항, 외부 동작, 구현 방식, 결정 이유, 일반 프로그래밍 개념 |

## 연결 원칙

- PRD는 관련 스펙과 안정된 요구사항 ID를 연결한다.
- 스펙은 PRD를 연결하고, 정확한 교환 형식은 계약으로 분리한다.
- 계약은 기준 스펙, 데이터를 만드는 쪽과 사용하는 쪽, 호환성 범위를 연결한다.
- 아키텍처 문서는 PRD·스펙·계약·ADR을 근거로 구조를 정리한다. 코드 지도와 모듈 설계는 코드 경로와 심볼(클래스·함수 이름)을 연결한다.
- ADR은 영향을 받는 기준 문서를 연결한다.
- 컨벤션은 관련 ADR과 아키텍처 문서를 연결한다.
- 해설과 how-to는 기준 문서를 바꾸지 않고 링크한다.
- 사고 기록은 당시의 기준 문서·버전과 관찰 결과를 연결한다. 기준을 바꾸는 후속 조치는 해당 문서에서 채택한 뒤 연결한다.
- 다른 문서는 용어집에 있는 용어를 다시 정의하지 않고 해당 용어집을 링크한다.
- 같은 사실의 기준 문서는 하나만 둔다.
- 시작 템플릿의 위치와 선택 기준은 해당 유형의 `AGENTS.md`에서 안내한다. 템플릿끼리 내용 기준으로 연결하지 않는다.
- 템플릿 저장소의 적용·갱신·도구 연결 안내는 템플릿 저장소의 루트 README에서 관리한다. 실제 프로젝트에 복사할 `docs/`에는 넣지 않는다.

아래 화살표 `A → B`는 A에서 정한 내용이 B의 근거가 된다는 뜻이다. B는 A를 링크하고 A의 결정을 바꾸지 않는다.

```text
PRD → 스펙 → 계약
PRD / 스펙 → ADR
PRD / 스펙 / 계약 / ADR → 아키텍처 문서(코드 지도·모듈 설계)
ADR / 아키텍처 문서 → 컨벤션
스펙 / 계약 / 아키텍처 문서 / 컨벤션 → 코드
모든 기준 문서 → 해설 / how-to
```

## 문서 작성과 목록 갱신

1. 독자가 답을 얻으려는 질문과 해당 문서의 소유 범위를 정한다.
2. 같은 질문을 다루는 기존 문서가 있는지 확인한다.
3. 새 문서가 필요하면 해당 디렉터리의 `AGENTS.md`에서 `docs/templates/`에 있는 시작 템플릿을 찾는다.
4. 필요한 항목을 프로젝트의 근거로 채우고, 실제 기준 문서와 요구사항 ID를 연결한다.
5. 작성한 실제 문서를 해당 디렉터리의 `README.md` 목록에 등록한다.
6. 링크·채택 범위·검증 증거·미결정 사항을 확인한다.

목록에는 작성한 프로젝트 문서만 등록한다. 템플릿과 작성 예정 문서는 등록하지 않는다. 문서가 없으면 빈 목록을 유지한다. 실제 문서는 작성한 기준 문서를 연결해야 한다. 복제와 자리표시자 처리는 [템플릿 원본 규칙](templates/AGENTS.md)을 따른다.

## 기준 문서 적용과 충돌 처리

문서의 존재와 채택 여부를 구분한다. 코드만 수정할 때도 아래 규칙을 적용한다. 상태 이름은 문서 유형별로 유지한다.

| 상태 또는 표시 | 구현할 때의 판단 |
| --- | --- |
| 초안 `Draft` · 제안 `Proposed` | 사용자 지시나 채택된 ADR에서 확정 근거를 찾는다. 근거가 있으면 상태 또는 채택 범위를 갱신한 뒤 적용한다. 이미 받은 결정을 다시 요청하지 않는다. |
| 적용 중 `Active` · 채택됨 `Accepted` | 문서가 정한 대상·버전·범위 안에서 기준으로 사용한다. 채택되었더라도 해당 변경에 영향을 주는 미결정 사항은 별도로 확인한다. |
| 사용 중단 예정 `Deprecated` | 신규 적용을 피하고, 명시된 기존 지원 범위와 대체 문서를 확인한다. |
| 지원 종료 `Retired` · 거절됨 `Rejected` · 대체됨 `Superseded` | 새 구현의 근거로 사용하지 않는다. 변경 이력을 확인할 때만 참조하고 현재 기준 문서를 찾는다. |
| 증거 대조 완료 `Verified` | 실제 구현이나 실행 결과와 대조했다는 뜻이다. 이 표시만으로 새 설계나 요구사항이 채택되었다고 판단하지 않는다. |
| 현재 `Current` · 목표 `Target` · 전환 중 `Transitional` · 과거 `Historical` | 구조의 시점이다. 채택 여부는 문서 상태와 근거 문서에서 별도로 확인한다. |

- 적용 상태가 없는 기준 문서는 첫 부분에 적용 범위와 채택 근거를 적는다. 해설·how-to·사고 기록은 연결된 기준을 따른다.
- 기준 문서가 없으면 사용자 요청·기존 문서·설정에서 확정된 내용을 찾아 기록한다. 기존 구현은 현재 동작의 증거이며, 목표 요구사항의 채택 근거로 단정하지 않는다.
- 문서나 코드가 다르면 적용 대상·버전·채택 상태·ADR을 확인한다. 내용별 기준은 위 [문서 배치](#문서-배치)를 따른다.
- 별도 변경 결정이 없으면 구현을 채택된 기준에 맞춘다. 기준 변경이 이미 사용자 지시에 포함되었으면 근거를 기록하고 진행한다. 새 결정이 필요하면 사용자에게 요청한다. 최근 수정 시각만으로 기준을 고르지 않는다.
- 해소할 근거가 없는 충돌은 내용·선택·영향을 제시한다. 영향받는 작업만 보류하고 나머지는 진행한다. 결정 후 문서와 구현을 함께 갱신한다.

## 검증 기록

- 스펙 시나리오와 테스트의 연결은 테스트 소스 코드의 메타 정보로 관리해야 한다. 어노테이션·태그에 `<specs/ 기준 상대 경로>:<시나리오 ID>` 값을 넣어야 한다. 스펙 파일이 `specs/` 바로 아래에 있으면 파일 이름만 쓴다. 하위 폴더에 있으면 `specs/`를 제외한 상대 경로를 쓴다(파일명은 확장자를 포함하며 하위 폴더는 `/` 구분자를 사용한다). 예: `login-screen.md:SCN-003`, `auth/login-screen.md:SCN-003`. 이를 지원하지 않는 프레임워크는 테스트 이름에 이 값을 넣을 수 있다. 한 테스트에 시나리오를 여러 개 연결할 수 있고, 한 시나리오에 테스트가 여러 개 있을 수 있다.
- 스펙의 수용 테스트 표에는 시나리오와 기대 결과를 정의해야 한다. 시나리오의 테스트 파일 위치·결과·실행 기록은 스펙 문서에 적지 않는다.
- 시나리오 커버리지와 시나리오별 결과는 메타 정보에서 생성해야 한다. 도구나 명령으로 스펙 수용 테스트 표의 시나리오 ID, 테스트 코드의 메타 정보와 테스트 실행 결과를 수집해야 한다. 보고서에는 테스트가 없는 시나리오를 `미연결`로, 존재하지 않는 시나리오를 가리키는 메타 정보를 `오류`로 표시해야 한다. 시나리오별 테스트의 통과·실패도 보고해야 한다.
- 구체적인 메타 정보 문법, 커버리지·결과 보고 명령, 보고서·CI 결과 위치는 프로젝트의 테스트 컨벤션에 정의해야 한다.
- 계약 테스트는 계약 문서에서, 문서·컨벤션·운영 검증은 검증 how-to나 해당 문서에서 관리한다. 다른 문서는 해당 보고서나 검증 기록을 링크한다.
- 테스트 실행·커버리지 보고서를 포함한 검증의 실행 기록에는 대상 버전·변경 범위, 환경, 명령 또는 확인 방법, 실제 결과를 적어야 한다. CI 실행 링크가 이 정보를 제공하면 링크로 대신할 수 있다.
- CI가 없으면 해당 보고서나 검증 문서에 로컬 실행 기록을 연결한다. 커밋이 있으면 함께 적는다. 커밋이나 테스트 파일 링크만으로 통과를 표시해서는 안 된다.
- 작업 트리에서 검증했으면 대상 커밋과 미커밋 변경 범위를 구분한다. 실행 결과는 `통과`·`실패`·`미실행`으로 표시한다. 미실행은 이유와 영향을 적는다.
- 구조 대조의 `Verified`에는 대조한 커밋 또는 작업 트리 범위와 확인 기록을 연결한다. 이 표시는 채택 여부나 동작 테스트의 통과를 대신하지 않는다.

## 작성 원칙

- 제목과 첫 문단만으로 목적과 범위를 알 수 있게 쓴다.
- 한 문서에는 하나의 주된 독자와 목적을 둔다.
- 수용 기준과 필수·금지 동작을 정한 문장은 관찰하거나 테스트할 수 있게 쓴다.
- 글쓰기와 용어 표기는 루트의 [쉬운 기술 글쓰기 규칙](../AGENTS.md#쉬운-기술-글쓰기)을 따른다.
- 미확정 값을 임의의 기본값으로 만들지 말고 책임자와 확정 위치를 기록한다.
- 같은 내용을 반복하지 않고 필요한 조건과 예외를 빠뜨리지 않는다.
- 현재 상태를 설명하는 문서는 문서 상태와 적용 범위에 맞는 요구사항·구조·절차를 중심으로 쓴다. 갱신할 때 과거 상태를 계속 덧붙이지 말고, 대체되거나 중복된 내용을 정리한다.
- 과거 내용은 현재 기준의 근거·제약·추적에 필요한 경우에만 유지한다. 결정·사고·검증처럼 보존 이유가 있는 내용은 해당 유형의 문서에 두고, 현재 문서에는 필요한 링크만 둔다.
- 과거 내용이 더는 근거나 제약을 설명하지 않으면 관련 문서에서 제거하거나 현재 상태에 맞게 고친다.
- 일반론보다 이 프로젝트에 필요한 정보, 제약과 판단을 우선하며 배경 지식이 길어지면 `explainers/`로 분리한다.
- 해설·코드 지도·모듈 설계처럼 사람이 코드를 따라가도록 돕는 문서를 작성하거나 고칠 때는 [`explain` 스킬](../.agents/skills/explain/SKILL.md)의 설명 순서와 쉬운 언어 규칙을 따른다. 설명한 코드 위치는 실제 파일과 심볼로 연결하고, 확인한 사실과 추정을 구분한다.

## 용어집

용어집은 이 프로젝트의 유비쿼터스 언어(ubiquitous language)를 기록한다. 유비쿼터스 언어는 DDD(도메인 주도 설계)에서 업무 담당자·기획자·개발자가 대화·문서·코드에서 같은 뜻으로 함께 쓰는 업무 언어다. 정의는 용어집 한 곳에 두고 다른 문서는 링크한다.

용어집은 `docs/` 밖에 둔다. 맥락(context)은 DDD의 바운디드 컨텍스트(bounded context)에 해당한다. 바운디드 컨텍스트는 하나의 도메인 모델과 유비쿼터스 언어가 일관되게 적용되는 경계다. 주문의 "취소"와 결제의 "취소"처럼 같은 단어의 뜻이 달라지면 맥락을 나누는 근거가 될 수 있다. 맥락이 하나면 루트 `GLOSSARY.md`를 쓴다.

### 용어집 위치

변경 대상의 맥락은 루트 `GLOSSARY-MAP.md`에서 찾는다. 용어집끼리 우선순위를 두지 않는다. 의존성과 빌드 결과 폴더를 제외하고 `GLOSSARY.md`를 검색해 맵과 대조한다.

| 저장소 상태 | 읽을 용어집과 할 일 |
| --- | --- |
| 루트에 `GLOSSARY-MAP.md`가 있음 | 맵의 맥락 목록에서 변경 대상이 속한 맥락의 용어집을 읽는다. 어느 맥락인지 불분명하면 사용자에게 묻는다. 맵에 없는 `GLOSSARY.md`가 있으면 맵에서 빠졌다고 보고한다. |
| 맵 없이 루트 `GLOSSARY.md`만 있음 | 맥락이 하나다. 루트 `GLOSSARY.md`를 읽는다. |
| 맵 없이 하위 폴더에 `GLOSSARY.md`가 있음 | 대상 폴더의 용어집과 루트 용어집이 있으면 읽는다. 맥락 구성이 불명확하므로 맵 누락을 알린다. 정의가 충돌하면 채택 근거를 확인한다. |
| 용어집이 없음 | 처음으로 용어를 확정할 때 루트 `GLOSSARY.md`를 만든다. 쓸 내용이 없으면 빈 파일을 미리 만들지 않는다. |

하위 용어집은 독립된 맥락에만 만든다. 맥락이 둘 이상이면 루트 맵이 있어야 한다. 공통 용어집도 맵에 등록한다. 용어집을 고치는 작업에서 맵 누락을 발견하면 같은 변경에서 보완한다.

### 용어집 형식

`GLOSSARY.md`는 다음 형식으로 쓴다.

```md
# {{맥락 이름}} 용어집

{{이 맥락이 무엇이고 왜 따로 있는지 한두 문장으로 쓴다.}}

## 용어

**{{용어}}({{코드에서 쓰는 영어 이름}})**:
{{무엇인지 한두 문장으로 정의한다.}}
_Avoid_: {{같은 개념을 가리키지만 쓰지 않을 표현}}
```

`GLOSSARY-MAP.md`는 다음 형식으로 쓴다. 맥락 목록의 링크는 맵 파일에서 각 용어집까지의 상대 경로다.

```md
# 용어집 맵

## 맥락

- [{{맥락 이름}}](./{{폴더 경로}}/GLOSSARY.md): {{이 맥락이 맡는 일}}

## 관계

- **{{맥락 A}} → {{맥락 B}}**: {{A가 B에 넘기는 사건·데이터와 그 이름}}
```

### 용어집 작성 규칙

- 이 프로젝트의 업무에만 있는 개념을 넣는다. 타임아웃, 오류 유형, 유틸리티처럼 일반 프로그래밍 개념은 프로젝트에서 자주 쓰더라도 넣지 않는다. 일반 기술 용어는 처음 나오는 문서에서 설명한다.
- 같은 개념에 이름이 여럿이면 하나를 고르고, 나머지는 `_Avoid_`에 적는다. 쓰지 않을 표현이 없으면 `_Avoid_` 줄을 지운다.
- 정의는 한두 문장으로 그 용어가 무엇인지만 쓴다. 도메인 지식이 없는 신입 개발자가 이해할 수 있는 쉬운 말로 쓴다.
- 용어집은 사전이다. 요구사항과 동작은 PRD·스펙에, 상태의 진입·종료 조건은 스펙에, 구현 방식은 코드 지도·모듈 설계에, 결정 이유는 ADR에 둔다.
- 코드에서 쓰는 영어 이름이 있으면 용어 뒤 괄호에 적는다. 새 코드 식별자는 이 이름을 따른다.
- 용어가 늘어 자연스러운 묶음이 생기면 `###` 소제목으로 나눈다. 모두 한 묶음이면 소제목 없이 나열한다.

### 용어집 유지보수

- 용어는 코드보다 먼저 PRD·스펙·ADR을 쓰는 시점에 정해야 한다. 이 문서들에 새 업무 개념이 나오면 용어집에 같은 개념이 있는지 확인한다. 없으면 이름과 뜻을 정해 같은 변경에서 용어집에 등록한다.
- PRD·스펙·ADR·코드는 해당 맥락의 정식 용어를 써야 한다. 현장에서 쓰는 다른 표현이나 동의어는 정식 용어의 `_Avoid_`에 기록해 대응 관계를 남긴다.
- 작업 중 용어가 확정되거나 뜻이 바뀌면 그 자리에서 용어집을 고친다. 작업 끝에 몰아서 고치지 않는다.
- 요청·문서·코드의 용어가 다르면 차이와 근거를 밝힌다. 결정할 근거가 없으면 사용자에게 확인한다.
- 한 단어가 여러 뜻으로 쓰이면 뜻마다 정확한 용어를 제안한다. 예: "계정"이 주문하는 고객인지 로그인한 사용자인지 구분한다.
- 이름이나 뜻을 바꾸면 관련 문서도 고친다. 코드 식별자의 변경 범위는 사용자 지시와 호환성 기준으로 판단한다. 남은 차이는 적용 범위나 미결정 사항에 기록한다.
- 맥락 폴더의 용어집을 추가·이동·삭제하면 `GLOSSARY-MAP.md`의 맥락 목록과 관계를 같은 변경에서 고친다.
- 용어의 뜻이 채택된 기준 문서와 충돌하면 [기준 문서 적용과 충돌 처리](#기준-문서-적용과-충돌-처리)를 따른다.

## 변경과 이동

- 기존 내용을 복제해 새 문서를 만들지 않고 기준 문서를 이동하거나 분리한다.
- 문서를 이동하거나 이름을 바꾸면 저장소 전체의 상대 링크를 함께 수정한다.
- 이전 주소에서 새 문서로 안내하는 문서는 외부 링크를 유지해야 할 명확한 이유가 있을 때만 남긴다.
- 구현·구조 변경에 따른 문서 갱신은 [작업 순서](../AGENTS.md#작업-순서와-필수-참조)를 따른다.

## 완료 점검

1. 문서가 올바른 디렉터리에 있는가?
2. 서로 다른 문서 유형의 관심사가 섞이지 않았는가?
3. 요구사항 ID와 기준 문서 링크가 유효한가?
4. 용어가 해당 [용어집](#용어집)의 이름·뜻과 일치하며, 작업 중 확정한 용어를 용어집에 반영했는가?
5. 상태, 적용 범위와 미결정 사항이 실제 채택 여부와 일치하는가?
6. [검증 기록](#검증-기록)에 따라 테스트 소스의 시나리오 메타 정보와 커버리지·결과 보고서, 실제 실행 증거를 연결했는가?
7. 내부 파일·제목 링크가 유효한가? 실제 문서는 템플릿이나 자리표시자 대신 채택된 기준을 연결하는가?
8. 소스 예제와 이름이 적용 중(`Active`)인 컨벤션을 따르는가?
9. 구조나 흐름이 바뀌었다면 코드 지도와 모듈 설계의 코드 경로·심볼이 실제 코드와 일치하는가?
