# 문서 작성 규칙

이 파일은 `docs/`와 모든 하위 디렉터리에 적용한다. [용어집](#용어집) 절은 저장소 어디에 있든 모든 `GLOSSARY.md`·`GLOSSARY-MAP.md`에 적용한다. 더 가까운 하위 `AGENTS.md`가 구체적인 규칙을 추가하며, 충돌하면 하위 규칙을 우선한다.

## 문서 배치

| 디렉터리 | 포함할 내용 | 포함하지 않을 내용 |
| --- | --- | --- |
| `requirements/` | 문제, 목표, 범위, 제약, 우선순위, 수용 기준 | 구현 선택, 상세 형식, 실행 절차 |
| `specs/` | 외부 동작, 상태 전이, 오류, 통신 절차, 화면 상태·입력 검증·화면 이동 | 선택의 역사, 장문의 배경, 정확한 API·메시지 형식 |
| `contracts/` | 데이터를 만드는 쪽과 사용하는 쪽, 교환 형식, 버전, 호환성 | 제품 배경, 전체 상태 전이, 운영 절차 |
| `architectures/` | 실제 코드 위치와 진입 흐름을 나타내는 코드 지도, 모듈 내부 책임·데이터·처리 순서, 구성요소·의존 관계·배포·보안 경계 | 사용자에게 보이는 동작, 정확한 교환 형식, 선택의 역사, 실행 절차 |
| `decisions/` | 배경, 결정, 대안, 결과, 재검토 조건 | 요구사항 복제, 사용 안내 |
| `explainers/` | 개념, 원리, 코드 구조와 데이터 흐름, 로딩 시점, 선택의 장단점 | 필수 동작이나 금지 사항, 작업 절차 |
| `conventions/` | 이름 짓기, 소스·테스트·서식 규칙과 준수 확인 방법 | 제품 동작, 구조 결정, 운영 절차 |
| `how-to/` | 전제 조건, 단계, 검증, 복구 | 결정 근거의 반복 설명 |
| `templates/` | 문서 작성을 시작할 때 복제하는 템플릿 원본 | 작성한 프로젝트 문서, 채택된 구현 기준, README 문서 목록 |
| `GLOSSARY.md`·`GLOSSARY-MAP.md` (저장소 루트 또는 맥락 폴더) | 업무 용어의 이름, 한두 문장 정의, 쓰지 않을 표현, 맥락 목록과 맥락 사이의 관계 | 요구사항, 외부 동작, 구현 방식, 결정 이유, 일반 프로그래밍 개념 |

## 연결 원칙

- 요구사항은 관련 시스템 스펙과 안정된 요구사항 ID를 연결한다. 화면 요구사항은 해당 화면 스펙의 경로와 시나리오 ID도 직접 참조한다.
- 시스템 스펙은 요구사항과 외부에서 관찰되는 동작을 정의하고, 별도 화면 스펙을 쓰면 해당 화면 스펙의 경로와 시나리오 ID만 연결한다.
- 화면 동작과 화면 수용 시험 행은 화면 스펙 한 곳에만 둔다. 관련 시스템 스펙이나 PRD에 같은 내용을 복제하지 않는다.
- 경계 계약은 기준 동작 명세, 데이터를 만드는 쪽과 사용하는 쪽, 호환성 범위를 연결한다.
- 코드 지도는 실제 파일·심볼·진입점과 대표 호출 흐름을 찾게 하며, 목표 구조(`Target`)와 구현된 구조(`Current`)를 구분한다.
- 모듈 설계는 한 모듈 내부의 책임·상태·자료 흐름·초기화·오류 처리를 설명하며, 여러 영역에 영향을 주는 결정은 ADR을 따른다.
- 구조 문서는 요구사항, 동작 명세, 경계 계약과 기술 결정 기록(ADR)의 결론을 특정 구조 질문에 답하는 관점별 문서로 조합한다.
- 시작 템플릿의 위치와 선택 기준은 해당 문서 유형의 `AGENTS.md`에서 안내한다. 템플릿은 실제 프로젝트 문서 목록에 등록하지 않는다.
- 같은 사실의 기준 문서는 하나만 둔다.

문서 사이의 화살표는 기준 근거와 연결 관계를 나타낸다. 오른쪽 문서가 왼쪽 문서의 책임이나 내용을 대신 정의하지 않는다.

```text
요구사항 → 동작 명세 → 경계 계약
요구사항 / 동작 명세 / 경계 계약 / 결정 기록 → 구조 문서
결정 기록 / 구조 문서 → 코드·산출물 작성 규칙
동작 명세 / 경계 계약 → 결정 기록 → 해설
동작 명세 / 경계 계약 / 결정 기록 → 실행 절차
```

## 기준 문서 적용과 충돌 처리

문서가 존재한다는 사실과 구현 기준으로 채택되었다는 사실을 구분한다. 다음 규칙은 루트 작업 지침에서 참조하며, 코드만 수정할 때도 적용한다. 문서 유형별 상태 이름은 유지하되 적용 여부는 다음과 같이 판단한다.

| 상태 또는 표시 | 구현할 때의 판단 |
| --- | --- |
| 초안 `Draft` · 제안 `Proposed` | 확정된 기준으로 단정하지 않는다. 사용자의 명시적인 확정 지시나 결정 기록으로 채택 여부를 확인하고, 해당 문서의 상태 또는 채택 범위를 갱신한 뒤 적용한다. |
| 적용 중 `Active` · 채택됨 `Accepted` | 문서가 정한 대상·버전·범위 안에서 기준으로 사용한다. 채택되었더라도 해당 변경에 영향을 주는 미결정 사항은 별도로 확인한다. |
| 사용 중단 예정 `Deprecated` | 신규 적용을 피하고, 명시된 기존 지원 범위와 대체 문서를 확인한다. |
| 지원 종료 `Retired` · 거절됨 `Rejected` · 대체됨 `Superseded` | 새 구현의 근거로 사용하지 않는다. 변경 이력을 확인할 때만 참조하고 현재 기준 문서를 찾는다. |
| 증거 대조 완료 `Verified` | 실제 구현이나 실행 결과와 대조했다는 뜻이다. 이 표시만으로 새 설계나 요구사항이 채택되었다고 판단하지 않는다. |
| 현재 `Current` · 목표 `Target` · 전환 중 `Transitional` · 과거 `Historical` | 구조를 설명하는 시점과 관점이다. 목표 구조라는 이유만으로 구현이 승인된 것은 아니며, 연결된 요구사항·결정 기록의 채택 범위를 확인한다. |

- 적용 상태가 정의되지 않은 문서 유형은 첫 부분에 기준으로 사용할 수 있는지와 적용 범위, 그 판단의 근거를 적는다. 해설과 실행 절차는 새 요구사항을 정하지 않고 연결된 기준 문서를 따른다. 모든 문서에 같은 상태 체계를 추가하지 않는다.
- 필요한 기준 문서가 없으면 기존 문서·설정·구현과 사용자 요청에서 확정된 내용을 찾아 해당 문서에 정리한다. 확정할 근거가 부족하면 임의로 요구사항을 만들지 않는다.
- 문서끼리 또는 문서와 코드가 다르면 적용 대상·버전·채택 상태·결정 기록을 먼저 확인한다. 요구사항은 필요한 결과, 동작 명세는 외부 동작, 경계 계약은 교환 형식의 기준이며, 구조 문서와 해설이 이를 임의로 바꾸지 않는다.
- 채택된 기준과 다른 구현은 별도의 변경 결정이 없는 한 기준에 맞춘다. 기준 자체를 바꿔야 한다면 사용자에게 변경 결정을 요청하고 근거 문서를 먼저 갱신한다. 현재 코드나 최근 수정 시각만을 근거로 문서를 덮어쓰지 않는다.
- 미결정 사항이나 충돌을 해소할 근거가 없으면 영향받는 작업만 멈추고, 충돌 내용·가능한 선택·영향을 사용자에게 제시해 결정을 요청한다. 영향받지 않는 작업은 진행할 수 있다. 결정 후에는 관련 문서와 구현을 함께 갱신한다.

## 작성 원칙

- 제목과 첫 문단만으로 목적과 범위를 알 수 있게 쓴다.
- 한 문서에는 하나의 주된 독자와 목적을 둔다.
- 수용 기준과 필수·금지 동작을 정한 문장은 관찰하거나 시험할 수 있게 쓴다.
- 공식 통신 규약 용어, 제품명, API 경로, 데이터 항목명, 측정 지표 이름과 코드 식별자는 원문을 유지하고 필요한 경우 백틱(`` ` ``)으로 감싼다. 처음 나올 때 쉬운 뜻과 현재 문서에서의 역할을 함께 설명한다. [용어집](#용어집)에 있는 용어는 용어집의 이름과 뜻을 그대로 쓴다.
- 미확정 값을 임의의 기본값으로 만들지 말고 책임자와 확정 위치를 기록한다.
- 결론을 뒤집는 결정은 기존 결정 기록을 덮어쓰지 않고 새 기록으로 대체한다.
- 문서 내용은 서로 중복되지 않으면서 필요한 내용을 빠뜨리지 않는 MECE(상호 배타적·전체 포괄) 원칙에 따라 구성한다.
- 일반론보다 이 프로젝트에 필요한 정보, 제약과 판단을 우선하며 배경 지식이 길어지면 `explainers/`로 분리한다.
- 코드 지도에는 실제 확인한 파일·심볼만 적고, 목표 구조를 구현 완료 사실처럼 표현하지 않는다. 모듈 설계는 호출 순서·자료 흐름·상태 소유자와 시작·종료 시점을 코드 근거와 연결한다.
- 다이어그램 화살표가 호출, 자료 전달, 처리 순서, source dependency 또는 문서 근거 중 무엇을 뜻하는지 표시한다.
- 독자가 결과와 문제를 먼저 이해한 뒤 실제 입력이 코드와 상태를 거쳐 결과가 되는 과정을 따라갈 수 있는 설명 문서를 작성하거나 고칠 때는 `explain` 스킬을 사용한다. 바이브 코딩 과정에서 놓치기 쉬운 전체 코드 구조와 호출 관계, 데이터·제어 흐름, 주요 초기화·로딩 시점, 결정 이유, 실패 조건과 구현 경계를 실제 파일·문서·테스트에 연결해 설명하고, 확인한 사실과 추정을 구분한다.

## 검증 기록

검증 기준과 전체 완료 명령은 [성능 및 검증](specs/performance-and-verification.md)을 따른다.

- 각 스펙 시나리오는 수용 시험 표에서 시험 파일·이름과 실행 기록을 연결한다. 계약 시험은 계약 문서에서 관리한다. 문서·컨벤션·운영 검증은 검증 how-to나 해당 문서에서 관리한다. 다른 문서는 그 기록을 링크한다.
- 실행 기록에는 대상 버전·변경 범위, 환경, 명령 또는 확인 방법, 실제 결과를 적는다. CI 실행 링크가 이 정보를 제공하면 링크로 대신할 수 있다.
- CI가 없으면 로컬 실행 기록을 연결한다. 커밋이 있으면 함께 적는다. 커밋이나 시험 파일 링크만으로 통과를 표시하지 않는다.
- 작업 트리에서 검증했으면 대상 커밋과 미커밋 변경 범위를 구분한다. 실행 결과는 `통과`·`실패`·`미실행`으로 표시한다. 미실행은 이유와 영향을 적는다.
- 구조 대조의 `Verified`에는 대조한 커밋 또는 작업 트리 범위와 확인 기록을 연결한다. 이 표시는 채택 여부나 동작 시험의 통과를 대신하지 않는다.

## 용어집

용어집은 프로젝트의 업무 용어 이름과 뜻을 정하는 기준이다. 같은 개념을 문서와 코드마다 다른 이름으로 부르면, 처음 읽는 사람은 문서와 코드를 연결하지 못한다. 그래서 용어의 뜻은 용어집에만 두고, 다른 문서는 용어집을 링크한다.

용어집은 문서 유형이 아니며 `docs/` 밖에 둔다. 맥락(context)마다 하나씩 둔다. 맥락은 한 단어가 같은 뜻으로 쓰이는 범위다. 예를 들어 주문 맥락의 "취소"와 결제 맥락의 "취소"는 뜻이 다를 수 있다. 대부분의 프로젝트는 맥락이 하나이므로 루트 `GLOSSARY.md` 하나만 둔다.

### 용어집 위치

작업을 시작할 때 변경 대상에 적용되는 용어집을 루트 `GLOSSARY-MAP.md` 기준으로 찾는다. 맵이 맥락 목록의 유일한 기준이며, 용어집 사이에 따로 우선순위를 두지 않는다. 맵과 실제 파일이 맞는지 확인하려고 저장소에서 `GLOSSARY.md` 파일 이름을 검색한다. 이때 `node_modules/` 같은 의존성 폴더와 빌드 결과 폴더는 제외한다.

| 저장소 상태 | 읽을 용어집과 할 일 |
| --- | --- |
| 루트에 `GLOSSARY-MAP.md`가 있음 | 맵의 맥락 목록에서 변경 대상이 속한 맥락의 용어집을 읽는다. 어느 맥락인지 불분명하면 사용자에게 묻는다. 맵에 없는 `GLOSSARY.md`가 있으면 맵에서 빠졌다고 보고한다. |
| 맵 없이 루트 `GLOSSARY.md`만 있음 | 맥락이 하나다. 루트 `GLOSSARY.md`를 읽는다. |
| 맵 없이 하위 폴더에 `GLOSSARY.md`가 있음 | 맥락이 여럿인데 맵이 빠진 상태다. 변경 대상 파일이 들어 있는 폴더의 용어집과 루트 `GLOSSARY.md`를 읽되, 어느 쪽도 우선하지 않는다. 같은 용어의 정의가 다르면 사용자에게 확인한다. 맵이 없다는 사실을 보고한다. |
| 용어집이 없음 | 처음으로 용어를 확정할 때 루트 `GLOSSARY.md`를 만든다. 쓸 내용이 없으면 빈 파일을 미리 만들지 않는다. |

하위 폴더 용어집은 그 폴더가 독립된 맥락일 때만 만든다. 맥락이 둘 이상이면 루트 `GLOSSARY-MAP.md`가 있어야 한다. 여러 맥락이 함께 쓰는 용어를 루트 `GLOSSARY.md`에 두는 경우에도 맵의 맥락 목록에 적는다. 맵이 빠졌거나 맵에 없는 용어집을 발견했고 용어집을 고치는 작업이면, 같은 변경에서 맵을 만들거나 고친다.

### 용어집 형식

`GLOSSARY.md`는 다음 형식으로 쓴다.

```md
# {{맥락 이름}} 용어집

{{이 맥락이 무엇이고 왜 따로 있는지 한두 문장으로 쓴다.}}

## 용어

**{{용어}}({{코드에서 쓰는 영어 이름}})**:
{{무엇인지 한두 문장으로 정의한다.}}
_Avoid_: {{같은 개념을 가리키지만 쓰지 않을 표현}}
```

`GLOSSARY-MAP.md`는 다음 형식으로 쓴다. 맥락 목록의 링크는 맵 파일에서 각 용어집까지의 상대 경로다.

```md
# 용어집 맵

## 맥락

- [{{맥락 이름}}](./{{폴더 경로}}/GLOSSARY.md): {{이 맥락이 맡는 일}}

## 관계

- **{{맥락 A}} → {{맥락 B}}**: {{A가 B에 넘기는 사건·데이터와 그 이름}}
```

### 용어집 작성 규칙

- 이 프로젝트의 업무에만 있는 개념을 넣는다. 타임아웃, 오류 유형, 유틸리티처럼 일반 프로그래밍 개념은 프로젝트에서 자주 쓰더라도 넣지 않는다. 일반 기술 용어는 처음 나오는 문서에서 설명한다.
- 같은 개념에 이름이 여럿이면 하나를 고르고, 나머지는 `_Avoid_`에 적는다. 쓰지 않을 표현이 없으면 `_Avoid_` 줄을 지운다.
- 정의는 한두 문장으로 그 용어가 무엇인지만 쓴다. 도메인 지식이 없는 신입 개발자가 이해할 수 있는 쉬운 말로 쓴다.
- 용어집은 사전이다. 요구사항과 동작은 PRD·스펙에, 상태의 진입·종료 조건은 스펙에, 구현 방식은 코드 지도·모듈 설계에, 결정 이유는 ADR에 둔다.
- 코드에서 쓰는 영어 이름이 있으면 용어 뒤 괄호에 적는다. 새 코드 식별자는 이 이름을 따른다.
- 용어가 늘어 자연스러운 묶음이 생기면 `###` 소제목으로 나눈다. 모두 한 묶음이면 소제목 없이 나열한다.

### 용어집 유지보수

- 작업 중 용어가 확정되거나 뜻이 바뀌면 그 자리에서 용어집을 고친다. 작업 끝에 몰아서 고치지 않는다.
- 사용자 요청, 문서, 코드의 용어가 용어집과 다르면 바로 밝히고 어느 쪽이 맞는지 확인한다. 예: "용어집은 '취소'를 주문 전체 취소로 정의하는데, 이번 요청은 일부 취소를 뜻하는 것 같습니다. 어느 쪽인가요?"
- 한 단어가 여러 뜻으로 쓰이면 뜻마다 정확한 용어를 제안한다. 예: "계정"이 주문하는 고객인지 로그인한 사용자인지 구분한다.
- 용어의 이름이나 뜻을 바꾸면 그 용어를 쓰는 문서를 같은 변경에서 고친다. 코드 식별자가 용어집과 달라지면 이름을 바꿀지 사용자에게 확인하고, 바꾸지 않으면 차이를 미결정 사항으로 남긴다.
- 맥락 폴더의 용어집을 추가·이동·삭제하면 `GLOSSARY-MAP.md`의 맥락 목록과 관계를 같은 변경에서 고친다.
- 용어의 뜻이 채택된 기준 문서와 충돌하면 [기준 문서 적용과 충돌 처리](#기준-문서-적용과-충돌-처리)를 따른다.

## 변경과 이동

- 기존 내용을 복제해 새 문서를 만들지 않고 기준 문서를 이동하거나 분리한다.
- 문서를 이동하거나 이름을 바꾸면 저장소 전체의 상대 링크를 함께 수정한다.
- 이전 주소에서 새 문서로 안내하는 문서는 외부 링크를 유지해야 할 명확한 이유가 있을 때만 남긴다.
- 구현이나 구조가 바뀌면 영향받은 요구사항, 동작 명세, 경계 계약, 코드 지도·모듈 설계·architecture view, 작성 규칙, 결정 기록, 해설과 실행 절차를 같은 변경에서 동기화한다.

## 완료 점검

1. 문서가 올바른 디렉터리에 있는가?
2. 서로 다른 문서 유형의 관심사가 섞이지 않았는가?
3. 요구사항 ID와 기준 문서 링크가 유효한가?
4. 용어가 해당 [용어집](#용어집)의 이름·뜻과 일치하며, 작업 중 확정한 용어를 용어집에 반영했는가?
5. 상태, 적용 범위와 미결정 사항이 실제 채택 여부와 일치하는가?
6. 각 변경 시나리오가 시험 위치와 실제 실행 증거에 연결되어 있으며, 미실행을 통과로 표시하지 않았는가?
7. 내부 상대 링크가 유효하며 템플릿 파일이나 자리표시자를 가리키는 링크가 남아 있지 않은가?
8. 소스 예제와 이름이 적용 중(`Active`)인 작성 규칙을 따르는가?
9. 코드 지도와 모듈 설계의 파일·심볼, Current/Target 구분과 실제 구현이 일치하는가?
10. 화면 스펙을 쓰는 경우 화면 동작·수용 시험의 기준 문서가 하나이며 다른 문서는 경로와 시나리오 ID만 참조하는가?
