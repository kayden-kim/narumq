# 문서 작성 규칙

이 파일은 `docs/`와 모든 하위 디렉터리에 적용한다. 더 가까운 하위 `AGENTS.md`가 구체적인 규칙을 추가하며, 충돌하면 하위 규칙을 우선한다.

## 문서 배치

| 디렉터리 | 포함할 내용 | 포함하지 않을 내용 |
| --- | --- | --- |
| `requirements/` | 문제, 목표, 범위, 제약, 우선순위, 수용 기준 | 구현 선택, 상세 형식, 실행 절차 |
| `specs/` | 외부 동작, 상태 전이, 오류, 통신 절차 | 선택의 역사, 장문의 배경 |
| `contracts/` | 데이터를 만드는 쪽과 사용하는 쪽, 교환 형식, 버전, 호환성 | 제품 배경, 전체 상태 전이, 운영 절차 |
| `architectures/` | 구성요소, 의존 관계, 데이터·처리 흐름, 권한 확인이 필요한 경계 | 선택의 역사, 정확한 교환 형식, 실행 절차 |
| `decisions/` | 배경, 결정, 대안, 결과, 재검토 조건 | 요구사항 복제, 사용 안내 |
| `explainers/` | 개념, 원리, 코드 구조와 데이터 흐름, 로딩 시점, 선택의 장단점 | 필수 동작이나 금지 사항, 작업 절차 |
| `conventions/` | 이름 짓기, 소스·테스트·서식 규칙과 준수 확인 방법 | 제품 동작, 구조 결정, 운영 절차 |
| `how-to/` | 전제 조건, 단계, 검증, 복구 | 결정 근거의 반복 설명 |

## 연결 원칙

- 요구사항은 관련 동작 명세와 안정된 요구사항 ID를 연결한다.
- 동작 명세는 요구사항을 연결하고, 정확한 교환 형식은 경계 계약으로 분리한다.
- 경계 계약은 기준 동작 명세, 데이터를 만드는 쪽과 사용하는 쪽, 호환성 범위를 연결한다.
- 구조 문서는 요구사항, 동작 명세, 경계 계약과 기술 결정 기록(ADR)의 결론을 특정 구조 질문에 답하는 관점별 문서로 조합한다.
- 결정 기록은 영향을 받는 기준 문서를 연결한다.
- 코드·산출물 작성 규칙은 관련 결정 기록과 구조 문서를 연결한다.
- 해설과 실행 절차는 기준 문서를 바꾸지 않고 링크한다.
- 같은 사실의 기준 문서는 하나만 둔다.

```text
요구사항 → 동작 명세 → 경계 계약
요구사항 / 동작 명세 / 경계 계약 / 결정 기록 → 구조 문서
결정 기록 / 구조 문서 → 코드·산출물 작성 규칙
동작 명세 / 경계 계약 → 결정 기록 → 해설
동작 명세 / 경계 계약 / 결정 기록 → 실행 절차
```

## 기준 문서 적용과 충돌 처리

문서가 존재한다는 사실과 구현 기준으로 채택되었다는 사실을 구분한다. 다음 규칙은 루트 작업 지침에서 참조하며, 코드만 수정할 때도 적용한다. 문서 유형별 상태 이름은 유지하되 적용 여부는 다음과 같이 판단한다.

| 상태 또는 표시 | 구현할 때의 판단 |
| --- | --- |
| 초안 `Draft` · 제안 `Proposed` | 확정된 기준으로 단정하지 않는다. 사용자의 명시적인 확정 지시나 결정 기록으로 채택 여부를 확인하고, 해당 문서의 상태 또는 채택 범위를 갱신한 뒤 적용한다. |
| 적용 중 `Active` · 채택됨 `Accepted` | 문서가 정한 대상·버전·범위 안에서 기준으로 사용한다. 채택되었더라도 해당 변경에 영향을 주는 미결정 사항은 별도로 확인한다. |
| 사용 중단 예정 `Deprecated` | 신규 적용을 피하고, 명시된 기존 지원 범위와 대체 문서를 확인한다. |
| 지원 종료 `Retired` · 거절됨 `Rejected` · 대체됨 `Superseded` | 새 구현의 근거로 사용하지 않는다. 변경 이력을 확인할 때만 참조하고 현재 기준 문서를 찾는다. |
| 증거 대조 완료 `Verified` | 실제 구현이나 실행 결과와 대조했다는 뜻이다. 이 표시만으로 새 설계나 요구사항이 채택되었다고 판단하지 않는다. |
| 현재 `Current` · 목표 `Target` · 전환 중 `Transitional` · 과거 `Historical` | 구조를 설명하는 시점과 관점이다. 목표 구조라는 이유만으로 구현이 승인된 것은 아니며, 연결된 요구사항·결정 기록의 채택 범위를 확인한다. |

- 적용 상태가 정의되지 않은 문서 유형은 첫 부분에 기준으로 사용할 수 있는지와 적용 범위, 그 판단의 근거를 적는다. 해설과 실행 절차는 새 요구사항을 정하지 않고 연결된 기준 문서를 따른다. 모든 문서에 같은 상태 체계를 추가하지 않는다.
- 필요한 기준 문서가 없으면 기존 문서·설정·구현과 사용자 요청에서 확정된 내용을 찾아 해당 문서에 정리한다. 확정할 근거가 부족하면 임의로 요구사항을 만들지 않는다.
- 문서끼리 또는 문서와 코드가 다르면 적용 대상·버전·채택 상태·결정 기록을 먼저 확인한다. 요구사항은 필요한 결과, 동작 명세는 외부 동작, 경계 계약은 교환 형식의 기준이며, 구조 문서와 해설이 이를 임의로 바꾸지 않는다.
- 채택된 기준과 다른 구현은 별도의 변경 결정이 없는 한 기준에 맞춘다. 기준 자체를 바꿔야 한다면 사용자에게 변경 결정을 요청하고 근거 문서를 먼저 갱신한다. 현재 코드나 최근 수정 시각만을 근거로 문서를 덮어쓰지 않는다.
- 미결정 사항이나 충돌을 해소할 근거가 없으면 영향받는 작업만 멈추고, 충돌 내용·가능한 선택·영향을 사용자에게 제시해 결정을 요청한다. 영향받지 않는 작업은 진행할 수 있다. 결정 후에는 관련 문서와 구현을 함께 갱신한다.

## 작성 원칙

- 제목과 첫 문단만으로 목적과 범위를 알 수 있게 쓴다.
- 한 문서에는 하나의 주된 독자와 목적을 둔다.
- 수용 기준과 필수·금지 동작을 정한 문장은 관찰하거나 시험할 수 있게 쓴다.
- 공식 통신 규약 용어, 제품명, API 경로, 데이터 항목명, 측정 지표 이름과 코드 식별자는 원문을 유지하고 필요한 경우 백틱(`` ` ``)으로 감싼다. 처음 나올 때 쉬운 뜻과 현재 문서에서의 역할을 함께 설명한다.
- 미확정 값을 임의의 기본값으로 만들지 말고 책임자와 확정 위치를 기록한다.
- 결론을 뒤집는 결정은 기존 결정 기록을 덮어쓰지 않고 새 기록으로 대체한다.
- 문서 내용은 서로 중복되지 않으면서 필요한 내용을 빠뜨리지 않는 MECE(상호 배타적·전체 포괄) 원칙에 따라 구성한다.
- 일반론보다 이 프로젝트에 필요한 정보, 제약과 판단을 우선하며 배경 지식이 길어지면 `explainers/`로 분리한다.
- 독자가 결과와 문제를 먼저 이해한 뒤 실제 입력이 코드와 상태를 거쳐 결과가 되는 과정을 따라갈 수 있는 설명 문서를 작성하거나 고칠 때는 `explain` 스킬을 사용한다. 바이브 코딩 과정에서 놓치기 쉬운 전체 코드 구조와 호출 관계, 데이터·제어 흐름, 주요 초기화·로딩 시점, 결정 이유, 실패 조건과 구현 경계를 실제 파일·문서·테스트에 연결해 설명하고, 확인한 사실과 추정을 구분한다.

## 변경과 이동

- 기존 내용을 복제해 새 문서를 만들지 않고 기준 문서를 이동하거나 분리한다.
- 문서를 이동하거나 이름을 바꾸면 저장소 전체의 상대 링크를 함께 수정한다.
- 이전 주소에서 새 문서로 안내하는 문서는 외부 링크를 유지해야 할 명확한 이유가 있을 때만 남긴다.
- 구현이나 구조가 바뀌면 영향받은 요구사항, 동작 명세, 경계 계약, 구조 문서, 작성 규칙, 결정 기록, 해설과 실행 절차를 같은 변경에서 동기화한다.

## 완료 점검

1. 문서가 올바른 디렉터리에 있는가?
2. 서로 다른 문서 유형의 관심사가 섞이지 않았는가?
3. 요구사항 ID와 기준 문서 링크가 유효한가?
4. 상태, 적용 범위와 미결정 사항이 실제 채택 여부와 일치하는가?
5. 각 변경 시나리오가 시험 위치와 실제 실행 증거에 연결되어 있으며, 미실행을 통과로 표시하지 않았는가?
6. 내부 상대 링크가 모두 유효한가?
7. 소스 예제와 이름이 적용 중(`Active`)인 작성 규칙을 따르는가?
