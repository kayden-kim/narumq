# Architecture Decision Record 작성 규칙

[상위 규칙](../AGENTS.md)을 따르며 다음을 추가한다.

- 상태는 최소 `Proposed`, `Accepted`, `Rejected`, `Superseded`를 구분한다.
- 결정, 배경, 결정 요인, 선택 근거, 대안, 결과, 검증과 재검토 조건을 기록한다.
- 대안은 같은 결정 요인으로 비교한다.
- 사실, 측정 결과, 가정과 판단을 구분한다.
- 긍정적·부정적 영향과 후속 작업을 함께 쓴다.
- Accepted ADR의 결론은 수정하지 않는다. 새 ADR로 대체하고 양방향 링크를 건다.
- 제품 요구, 상세 외부 동작과 실행 절차를 ADR에 복제하지 않는다.

## 추가 작성 지침

- **파일명과 식별:** `ADR-NNNN-short-title.md` 형식을 사용하며, 번호는 생성 순서대로 증가시키고 재사용하지 않는다.
- **권장 구조:** 결정 → 배경 → 결정 요인 → 선택 근거 → 대안 → 결과 → 검증 → 재검토 조건 순서로 구성하되, 결정, 근거, 결과와 상태는 생략하지 않는다.
- **Accepted ADR 변경 통제:** Accepted ADR은 오탈자, 링크와 사실 보정만 수정하며 결론을 변경하지 않는다. 결론 번복 시 새 ADR을 작성하고 기존 ADR을 Superseded로 처리한다.
- **메타데이터 테이블 규약:** 상단 메타데이터 표에는 상태, 결정(제안)일, 결정자, 관련 요구사항, 관련 스펙·Contract, 관련 Architecture 외에 **관련 해설**(`docs/explainers/` 링크) 행을 포함한다. 이는 도메인 및 기술 배경지식이 부족한 주니어 개발자가 해당 결정의 핵심 이론과 동작 메커니즘을 즉시 학습할 수 있도록 돕기 위함이다.
