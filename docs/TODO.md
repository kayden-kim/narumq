# PRD 구현 잔여 작업

이 문서는 [PRD](requirements/PRD.md)의 구현·수용 시험·선행 결정 잔여 작업을 요구사항 ID 기준으로 추적한다. 범위는 MQTT·클라이언트 호환성, cluster/session, tenancy/security, management/observability, deployment, performance와 verification 전반이다. 기존 cluster backlog는 상태와 근거를 보존해 포함한다.

PRD는 `Draft` 상태이므로 이 목록은 요구사항을 구현 기준으로 채택했다는 뜻이 아니다. 구현 범위와 완료 판정은 채택된 스펙·계약·ADR 및 연결된 수용 시험을 따른다. 시험 명령, 실행 시간, run ID 같은 증거는 각 기준 문서의 수용 매핑에 기록하고 이 목록에는 반복하지 않는다.

| 표기 | 뜻 |
| --- | --- |
| `[ ]` | 열린 작업이다. 착수 전 링크한 기준 문서에서 범위를 확인한다. |
| `[ ]` **보류** | 외부 결정이나 실행 환경이 없어 착수하지 않는 작업이다. 보류 사유와 해제 조건을 함께 적는다. |
| `[x]` | 적힌 범위의 수용 시험을 통과했다. 범위 밖 gate는 §1의 열린 작업으로 따로 추적한다. |

열린 항목의 **미구현**은 필요한 기능이 없다는 뜻이고, **부분 구현**은 현재 기능이 요구 범위의 일부만 충족한다는 뜻이다. **결정 필요**는 구현·시험 전에 정책이나 계약을 확정해야 하며, **미검증**은 구현 증거가 있어도 해당 수용 시험은 남아 있다는 뜻이다. 후속 ADR과 최신 수용 매핑에서 해결된 과거 항목은 다시 열지 않는다.

### 1.1 Production storage와 disaster recovery

2026-10-03에는 실제 인프라 시험을 보류하기로 결정했으나, 이후 시험 재개 지시에 따라 2026-10-14 EKS live 실측을 수행했다. PRD §18 질문 16의 `EKS_EC2_HA` ARM64 qualification profile은 [ADR-0007](decisions/ADR-0007-aws-production-deployment-platform.md)과 [EKS architecture](architectures/eks-ec2-deployment.md)에 정의했다: EKS `1.37`, `m7g.large` worker 3대(AZ별 1대), broker별 20 GiB `gp3` EBS(3,000 IOPS / 125 MiB/s), NLB `IP` target/TCP listener, broker별 requests=limits `1 CPU`·`4 GiB`. Profile 정의와 제한된 라이브 실측은 production workload·storage 적합성이나 전체 인프라 수용 완료를 뜻하지 않는다. 아래 두 항목이 닫히기 전에는 CLU-14, [ADR-0009 §7](decisions/ADR-0009-raft-production-state-profile.md#7-검증)의 production 행과 [ADR-0003 §9](decisions/ADR-0003-durable-ack-barrier.md#9-검증) 전체를 완료로 표시하지 않는다.

- [ ] **미검증 · [K8s/AWS 인프라 테스트 필요]** — Linux/EBS 전원·volume 손실 수용: 지원 Linux filesystem과 Amazon EBS에서 전원 손실 뒤 마지막 durable commit 보존, production WAL torn-tail 판정, volume loss/reseed를 시험한다.
  - 부분 검증: 2026-10-14 EKS live에서 실제 영속 volume 손실이 아닌 disposable `emptyDir`를 사용해 member 3 bootstrap guard refusal만 확인했다. Member 1의 PROGRESSED 응답(term 6, commit index 100) 뒤 `cluster bootstrap refused`와 exit 1, emptyDir 내 파일 미생성 및 기존 3개 broker 3/3 Ready 유지를 관찰했다. Durable ACK/data 보존, 실제 EBS detach/reattach·power loss, production WAL torn-tail 및 volume loss/reseed recovery는 시험하지 않았다(ADR-0022, CLU-14 §11.20).
  - 2026-10-15 격리 EKS 전원 손실 시도 — **FAILED/UNRESOLVED (PASS 아님)**: 장애 주입 전 QoS 1 retained marker의 `PUBACK`(Reason Code 0)을 확인했고 기준 snapshot 3개는 모두 `completed`였다. `--skip-os-shutdown` stop/start 뒤 원래 fixture instance `i-01ee5c360cbebe3bc`는 종료됐으며 동일한 암호화 EBS volume `vol-0ffad539c1775d890`이 Auto Scaling group(ASG) 대체 instance `i-0943ccdd52161cb1d`에 연결됐다. 300초 읽기 전용 후속 관찰에서 member3은 `VOTER/FOLLOWER DRAINING/NotReady`, 적용 인덱스(`applied index`) `64`였다. quorum은 `2/3`이었고 retained marker의 SHA-256 `a9bcdbc10589498426e43191fca05fd0793038860001964776b5d84fe8403488`은 voter `1`·`2`에서만 확인했다.

  - 정리 결과: 격리 시험 환경의 EKS cluster/VPC, 세 EBS volume `vol-003fd51c4a6a90d19`·`vol-0452cccc5a9b6f927`·`vol-0ffad539c1775d890`, CloudWatch log group `/aws/eks/narumq-ha-acceptance-20261014/cluster`, task 전용 ECR tag `profile-diagnostic-20261014-1247`·`profile-diagnostic-opt-20261014-1326` 및 그에 속한 4개 untagged ARM64·attestation digest를 제거했다. 두 task index digest도 부재를 확인했다. task image digest 6개 모두 ECR에서 찾을 수 없고(tagged/untagged 참조 없음), 공유 `observability-20261014` tag와 그 index·ARM64 digest는 계속 존재한다. 기준 snapshot `snap-01999990697d01221`·`snap-0e3a75c648325b3cd`·`snap-059315c3eb5c3bae4`는 의도적으로 보존했다. `narumq-eks`는 `ACTIVE`로 관찰됐다. - [ ] **로컬 S3 구현·검증 준비 완료 / 실제 환경 수용 미검증 · [K8s/AWS 인프라 시험 필요]** — 백업 보존 기간과 재해 복구 RPO/RTO(`SPEC-TBD-09`): 2026-10-13 확정 정책은 하루 1회 백업·30일 보존, RPO 24시간·RTO 1시간이다.
  - 기존 부분 검증: 백업 CronJob(`0 2 * * *`) 배포, 온라인 NMQBKUP3 archive(Format 3.0, Commit Index 100), 세 voter의 오프라인 `-cluster-restore` 시드 절차(총 0.070초)를 확인했다. 이는 전체 RTO 측정이 아니다.
  - 2026-10-14 보존 정리 스크립트 부분 검증: 실제 backup PVC에 빈 임시 파일 `backup-retention-probe-20261014.nrbak`을 만들고 `mtime`을 2026-09-12 05:59:19 UTC로 설정한 뒤 CronJob 템플릿에서 만든 수동 Job(`narumq-backup-retention-20261014`)을 실행했다. Job 성공 후 임시 파일만 사라졌고 기존 두 archive(`backup-20261014030907.nrbak`, `backup-20261014032303.nrbak`)는 남았으며 새 archive `backup-20261014055926.nrbak`가 생성됐다. 이는 `mtime`을 인위적으로 바꾼 스크립트 동작 확인이며 실제 정기 CronJob 실행·주기를 입증하지 않는다.
  - 2026-10-15 KST 로컬 S3 경로 구현·준비 완료(실제 환경 수용은 아님): 별도 `deploy/terraform-acceptance-s3` 로컬 backend/state와 전용 S3 모듈의 Terraform 코드에 같은 AWS 리전의 비공개 버킷, 퍼블릭 접근 차단, TLS 연결만 허용, S3 관리형 암호화(SSE-S3), 30일 만료·1일 미완료 multipart upload 중단, 업로드 역할의 `PutObject` 전용 권한, 복원 역할의 지정 prefix에 한정한 `ListBucket`·`GetObject` 권한을 정의했다. 이는 코드 설정 검토 결과이며 AWS 리소스는 만들지 않았다. 기존 backup API와 archive 구현은 유지한다. CronJob은 기존 헤더와 NMQBKUP3 무결성 검증 뒤 PVC에 요청 기록이 있는 archive만 업로드하고, 실패 때 archive와 요청을 보존하며 S3 checksum 응답을 확인한 뒤에만 삭제한다. 요청 기록이 없는 기존 archive는 자동 이관하지 않고 `mtime +30` 로컬 정리 경계를 유지한다. 복원 절차는 prefix에서 정확한 객체 키를 선택하고 검증·다운로드한 뒤 빈 격리 대상에서 기존 offline restore를 실행한다. 상세 동작은 [§10](specs/cluster-session-and-delivery.md#10-snapshot-backup과-restore), [§11.9](specs/cluster-session-and-delivery.md#119-offline-queue-replication과-backup-v3-수용-매핑), [ADR-0058](decisions/ADR-0058-cluster-backup-s3-retention-and-restore.md)에 있다.
  - 배포 opt-in 경계(2026-10-15 KST): 기본 `deploy/kubernetes/eks-ec2-ha` overlay는 로컬 백업만 유지한다. ### 1.5 설계 미결정과 비지원 범위

[Cluster architecture의 미결정 사항](architectures/cluster-architecture.md#미결정-사항)은 과거 target과 현재 구현을 함께 언급한다. 아래 경계는 새 기능의 구현 승인이 아니며, 현재 지원 범위를 넓힐 때 먼저 결정해야 할 사항이다.
- Route-index 물리적 배치와 rebuild 방식: 현재 node-local projection rebuild는 [Cluster §11](specs/cluster-session-and-delivery.md#11-수용-시험)의 수용 범위에서 완료했다. Architecture의 물리적 배치 질문을 기존 rebuild 미구현으로 다시 열지 않는다. 별도 분산 배치나 rebuild 방식 변경이 필요하면 [ADR-0009 §1.4](decisions/ADR-0009-raft-production-state-profile.md#14-consensus-group-partition-profile)의 단일 group·node-local projection과의 관계, ordering과 routing readiness를 먼저 확정한다.
- Active peer transport 밖 RPC encoding: 관측 snapshot 조회는 사용자가 채택한 [Peer observability v1 contract](contracts/peer-observability-v1.md)에 producer·consumer, 형식·한도·인증·version 범위를 정의한다. 이 구현을 제외한 새 RPC는 도입 전에 같은 항목을 별도 계약으로 정한다. Persisted schema 계약은 [Replicated-state v1](contracts/replicated-state-v1.md)에서 완료했으며 미래 major migration은 별도 계약을 먼저 정한다.
- Cross-cluster migration과 3-bootstrap-voter identity 제한 밖 restore: [Cluster §10](specs/cluster-session-and-delivery.md#10-snapshot-backup과-restore)의 현재 비지원 범위다. V1/v2 archive, learner를 포함한 archive와 voter-set 변경도 현재 restore로 지원하지 않는다. 별도 migration·identity 계약의 채택 없이 자동으로 구현 백로그에 넣거나 CLU-14의 현 수용 범위로 포함하지 않는다.
