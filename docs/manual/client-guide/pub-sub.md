# 메시지 발행 및 구독 가이드

| 항목 | 내용 |
| :--- | :--- |
| **대상 독자** | NaruMQ에서 메시지를 주고받는 MQTT 애플리케이션 개발자 |
| **문서 목적** | 토픽 명명 규칙, 와일드카드 구독, QoS 전달 보장 수준, Retained 메시지 동작을 이해한다. |
| **지원 버전** | MQTT v3.1.1, MQTT v5.0 |

## 1. 토픽(Topic) 규칙 및 와일드카드

MQTT는 토픽 기반의 발행-구독(Pub/Sub) 모델을 사용합니다. 발행자와 구독자는 토픽 경로를 통해 메시지를 주고받습니다.

### 토픽 이름 규칙
- **계층 구분자 (`/`):** 토픽 레벨은 슬래시로 구분합니다. (예: `factory/line1/machineA/status`)
- **대소문자 구분:** `sensor/temp`와 `Sensor/Temp`는 서로 다른 토픽입니다.
- **공백 및 특수문자:** 공백이나 제어 문자는 피하고, 영숫자, 하이픈(`-`), 언더스코어(`_`) 사용을 권장합니다.
- **시스템 토픽 (`$`):** `$`로 시작하는 토픽(예: `$SYS/`)은 시스템 내부 예약 토픽이므로 클라이언트가 직접 발행할 수 없습니다.

### 구독용 와일드카드
메시지를 구독할 때 여러 토픽을 한 번에 수신하기 위해 와일드카드를 사용할 수 있습니다. 와일드카드는 **구독 시에만 사용 가능**하며, 메시지를 발행할 때는 사용할 수 없습니다.

| 와일드카드 | 설명 | 사용 예시 | 매칭되는 토픽 예시 |
| :--- | :--- | :--- | :--- |
| **단일 레벨 (`+`)** | 정확히 하나의 토픽 계층과 일치합니다. | `sensor/+/temperature` | `sensor/livingroom/temperature`<br>`sensor/kitchen/temperature`<br>*(매칭 안 됨: `sensor/floor1/room1/temperature`)* |
| **다중 레벨 (`#`)** | 이후의 모든 하위 토픽 계층과 일치합니다. 토픽 필터의 맨 마지막에만 위치해야 합니다. | `sensor/#` | `sensor/temp`<br>`sensor/kitchen/humidity`<br>`sensor/a/b/c/d` |

## 2. 서비스 품질 수준 (QoS - Quality of Service)

MQTT는 세 가지 QoS 수준을 제공합니다. 애플리케이션의 신뢰성 요구사항에 맞춰 QoS를 선택합니다.

| QoS 레벨 | 이름 | 설명 | 특징 및 패킷 흐름 |
| :--- | :--- | :--- | :--- |
| **QoS 0** | At most once (최대 1회) | 메시지를 1회 전송하며 수신 확인(ACK)을 기다리지 않습니다. | 네트워크 장애 시 유실 가능. 가장 빠르고 가벼움. (`PUBLISH`) |
| **QoS 1** | At least once (최소 1회) | 수신자로부터 `PUBACK`을 받을 때까지 재전송합니다. | 유실은 없으나 중복 수신 가능. (`PUBLISH` ↔ `PUBACK`) |
| **QoS 2** | Exactly once (정확히 1회) | 4단계 핸드셰이크를 거쳐 중복과 유실 없이 정확히 1회 전달합니다. | 가장 엄격한 전달 보장. (`PUBLISH` ↔ `PUBREC` ↔ `PUBREL` ↔ `PUBCOMP`) |

::: tip 단일 노드 런타임의 QoS 지원 및 메모리 경계 안내
NaruMQ 단일 노드 standalone 프로세스(`cmd/narumq`)는 프로세스 메모리 내에서 **QoS 0, QoS 1, QoS 2 프로토콜 핸드셰이크를 모두 온전히 지원**합니다.

- **QoS 1 핸드셰이크:** 메시지 수신 후 fan-out 성공 시 `PUBACK`을 반환하며, 중복 패킷 재전송 시 중복 전달 없이 일관된 `PUBACK`을 응답합니다.
- **QoS 2 핸드셰이크:** 1단계 `PUBREC` 응답 및 클라이언트의 `PUBREL` 수신 후 실제 fan-out 및 `PUBCOMP` 완료까지 4단계 교환을 지원합니다.
- **인메모리 경계:** standalone 프로세스는 디스크 WAL이나 복제 합의가 아닌 프로세스 메모리(RAM)에 세션 및 전달 큐를 보관합니다. 따라서 기동 로그에 `"qos0_only": true`가 표시되더라도 실제 프로토콜 핸드셰이크는 QoS 0/1/2를 모두 처리하며, 프로세스 재시작 시에는 메모리 상태가 초기화되어 미완료 메시지가 유실될 수 있습니다.
- **분산 영속 내구성 (Durable ACK):** 노드 장애 및 프로세스 재시작 시에도 RPO 0을 보장하는 디스크/Raft 복제 기반 Durable ACK는 [Raft 클러스터 런타임](../cluster-preview/cluster-preview.md)의 대상입니다.
:::

## 3. Retained 메시지

메시지 발행 시 `retain = true` 플래그를 설정하면 브로커는 해당 토픽의 마지막 유효 메시지를 보관합니다.

- **동작 방식:** 새로운 클라이언트가 해당 토픽을 나중에 구독하더라도, 구독 승인 즉시 마지막으로 보관된 Retained 메시지를 전달받습니다.
- **상태 초기화:** 빈 페이로드(0 바이트)를 `retain = true`로 발행하면 해당 토픽의 Retained 메시지가 삭제됩니다.
- **주요 활용 사례:** 디바이스의 최신 상태값(온도, 전원 On/Off 등), 시스템 설정값 등 신규 접속자에게 현재 상태를 즉시 알려야 할 때 유용합니다.

## 4. 인가 및 접근 제어 (Default-Deny ACL)

보안 모드로 동작하는 NaruMQ 브로커는 **Default-Deny(기본 차단)** 원칙을 따릅니다.

1. 클라이언트가 특정 토픽에 `PUBLISH` 또는 `SUBSCRIBE`를 시도하면, 브로커는 클라이언트 인증 정보에 연결된 ACL 정책을 확인합니다.
2. 명시적으로 허용 규칙이 등록되어 있지 않은 토픽에 대한 발행/구독 요청은 즉시 차단됩니다.
3. 비인가 요청 발생 시 브로커는 보안 감사 로그에 거부 이벤트를 기록합니다.
