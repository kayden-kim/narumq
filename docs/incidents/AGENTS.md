# 사고 기록 작성 규칙

[상위 규칙](../AGENTS.md)을 따르며 다음을 추가한다.

## 시작 템플릿

[사고 기록 템플릿](../templates/incident.template.md)로 실제 사건을 기록한다.

## 작성 규칙

- 장애·배포 실패·데이터 문제 등 영향·복구·원인·후속 조치를 별도로 추적할 사건에 작성한다. 모든 결함 수정에 사고 기록을 만들 필요는 없다.
- 파일명은 `INC-YYYYMMDD-NN-short-title.md`로 쓴다. 날짜는 발견일이며, 같은 날짜 안의 번호를 재사용하지 않는다.
- 발생·발견·완화·복구 시각을 구분한다. 시간대 또는 UTC 오프셋을 적는다. 추정 시각은 근거와 함께 표시한다. 모르면 미확인으로 적는다.
- 영향·원인·대응 결과는 사실과 가설을 구분한다. 원인이 불확실하면 남은 질문과 확인 방법을 적는다. 계획한 조치는 수행 경과에 넣지 않는다.
- 사건 발생 당시의 관련 기준 문서와 코드·배포 버전을 연결한다. 현재 기준과 당시 기준이 다르면 차이를 표시한다.
- 반복할 복구 절차는 how-to에 둔다. 사고 기록에는 이번에 수행한 조치·관찰 결과와 해당 절차를 연결한다.
- 후속 조치에는 담당자·기한·완료 조건·추적 위치를 적는다. 기준 변경은 해당 문서에 반영한다. 기술 선택은 [ADR 작성 조건](../decisions/AGENTS.md)을 따른다.
- 회귀 테스트의 증거는 [검증 기록](../AGENTS.md#검증-기록)에 따른 테스트 메타 정보 기반 커버리지·결과 보고서를 연결한다. 사고 기록에 같은 테스트 결과를 복제하지 않는다. 운영 복구의 증거와 회귀 테스트의 증거는 구분한다.
- 비밀 값이나 실제 개인정보가 포함된 로그를 본문에 복사하지 않는다. 필요한 증거는 민감정보를 제거한 기록의 위치와 확인 범위를 연결한다.

## 기록 상태

기록의 검토 상태와 서비스의 복구 상태를 구분한다. 아래 상태는 사고 기록의 완성도를 나타내며 기준 문서의 채택 상태가 아니다.

| 기록 상태 | 의미 |
| --- | --- |
| 작성 중 | 사실·원인·대응과 후속 조치를 정리하거나 검토하는 중이다. |
| 검토 완료 | 확인 가능한 내용과 증거를 대조했고, 미확인 사항과 후속 조치의 담당자·추적 위치를 남겼다. |

복구 여부는 관찰 결과에서 확인한다. 후속 조치의 완료 여부는 추적 위치에서 확인한다. 검토 뒤 새 사실을 추가하면 근거와 재검토 결과를 남긴다.
