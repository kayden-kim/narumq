# 기술 해설 작성 규칙

[상위 규칙](../AGENTS.md)을 따르며 다음을 추가한다.

- 기준 독자와 읽고 나면 답할 수 있는 질문 2~4개를 밝힌다.
- 주니어 개발자가 독립적으로 이해할 수 있도록 배경, 전제와 용어 간 관계를 생략하지 않고 충분한 맥락과 함께 상세히 설명한다.
- 구체적인 문제 상황에서 시작해 용어, 정상 흐름, 실패 흐름 순서로 설명한다.
- 전문 용어와 약어는 처음 등장할 때 정의한다.
- 상태의 owner, 저장 위치, 생성 시점과 제거 시점을 함께 밝힌다.
- 실패 뒤 남는 상태, retry 가능 여부와 보장하지 않는 범위를 설명한다.
- 프로젝트에서 찾을 source·기준 문서를 연결한다.
- 규범 요구, 아키텍처 결정이나 실행 절차를 새로 만들지 않는다.
- 버전에 따라 달라지는 사실은 대상 버전, 확인일과 공식 출처를 쓴다.

## 추가 작성 지침

- **기준 독자:** Go 문법, HTTP/TCP 기초는 알고 있으나 MQTT broker, 분산 합의, durable storage, Kubernetes 운영 경험이 부족한 주니어 개발자를 대상으로 한다.
- **권장 구조:** 1. 한눈에 보는 답 → 2. 읽고 나면 답할 수 있는 질문(2~4개) → 3. 문제 상황 → 4. 필수 용어 → 5. 정상 흐름 → 6. 실패 흐름(남는 상태, retry 가능 여부) → 7. 오해와 trade-off → 8. NaruMQ에서 찾을 위치(package, spec, ADR) → 9. 확인 질문 → 10. 참고 자료.
- **주제 선정 및 Backlog:** 둘 이상의 기준 문서에 반복 등장하거나, 오해 시 데이터 손실·split-brain 위험이 있는 선행 개념을 선정하여 README backlog에 관리한다.
