NaruMQ / 코드로 읽는 검증 게이트

코드 변경이 `PASS`가 되기까지

이 문서는 NaruMQ의 현재 local·CI verification gate를 명령 목록으로만 나열하지 않습니다. local·CI에서 10개 검증 command를 병렬 실행하고 coverage policy를 평가하는 흐름, 그리고 별도 수동 mutation command가 다섯 핵심 package의 test 민감도를 확인하는 과정을 실제 코드와 기준 문서에 연결해 설명합니다.

01 · 결과부터

게이트의 결과는 숫자 하나가 아니라, 재현 가능한 증거 묶음이다

개발자는 저장소 루트에서 go run ./tools/verify local 또는 go run ./tools/verify ci --base <merge-base>를 실행합니다. 두 gate는 coverage, race, fuzz와 사전 검사를 수행합니다. Mutation은 자동으로 실행하지 않습니다. 필요하면 go run ./tools/verify mutation을 별도로 실행합니다.

성공의 의미

모든 command가 exit code 0으로 끝났고, 각 gate가 요구하는 artifact를 만들었다는 뜻입니다. 하나의 평균 점수가 모든 품질을 대신하지 않습니다.

실패의 의미

병렬 command 중 실패가 나면 runner가 나머지 작업의 cancellation을 요청하고 실패 결과를 모읍니다. 병렬 단계가 실패하면 후속 coverage policy 검사는 실행되지 않습니다.

혼동하면 안 되는 것

Coverage 숫자가 높아도 traceability가 실패하면 local·CI gate는 통과하지 않습니다. Mutation은 다른 질문에 답하지만 자동 gate에는 포함하지 않습니다. 필요할 때 별도 명령으로 확인합니다.

02 · 배경 개념

각 검사는 서로 다른 질문에 답한다

verification gate는 같은 코드를 여러 번 실행하는 과정이 아닙니다. 정상 입력, 비정상 입력, 동시성, 요구사항 연결, package 경계, 실행되지 않은 코드와 약한 assertion을 서로 다른 방법으로 확인합니다.

검사쉬운 질문현재 gate가 확인하는 것
unit정상·오류·경계 입력에서 결과가 맞는가?전체 package test를 한 번 실행합니다.
fuzz사람이 고른 예시 밖의 입력에서도 invariant가 깨지지 않는가?MQTT codec 2개, routing, session과 TCP input을 고정 quota로 실행합니다.
race동시에 접근할 때 data race가 생기지 않는가?전체 package를 race detector로 다시 실행합니다.
traceability지원한다고 선언한 규격·요구사항에 실제 test가 연결됐는가?source의 `Traceability` metadata와 conformance matrix를 양방향 비교합니다.
architecturepackage가 허용되지 않은 방향으로 의존하지 않는가?현재 `go list` import graph를 domain·application·adapter 경계와 비교합니다.
coverage실행 가능한 production code가 실제로 실행됐는가?atomic coverprofile과 policy floor·ratchet·CI diff를 평가합니다.
mutationtest assertion이 production 조건의 변화를 실제로 잡는가?go run ./tools/verify mutation이 Delivery·MQTT·NodeDrain·Security·Session을 확인합니다. 수동 실행이며 local·CI에는 포함되지 않습니다.
이 구분이 필요한 이유는 “실행됐다”와 “검증됐다”가 다르기 때문입니다. 예를 들어 line coverage는 한 줄이 실행됐다는 사실을 보여주지만, 그 줄의 조건을 반대로 바꿨을 때 test가 실패하는지는 mutation이 확인합니다.
03 · runner 흐름

`main.go`는 local·CI와 수동 mutation을 서로 다른 runner에 연결한다

`tools/verify/main.go`는 subcommand를 고릅니다. `local`과 `ci`는 `runVerification`을 공유합니다. CI는 diff base를 coverage command에만 전달합니다. 수동 `mutation` 명령은 별도 `runMutation` 흐름에서 다섯 Gremlins package를 실행합니다. 

// tools/verify/runner.go:44-125
func runLocal(ctx context.Context, root string, runner commandRunner) error {
    return runVerification(ctx, root, verificationOptions{}, runner)
}

func runCI(ctx context.Context, root, base string, runner commandRunner) error {
    if strings.TrimSpace(base) == "" {
        return fmt.Errorf("ci requires --base <git-ref>")
    }
    return runVerification(ctx, root, verificationOptions{CI: true, Base: base}, runner)
}

func runVerification(...) error {
    // local/CI parallel checks followed by coverage policy; no mutation
}

func runMutation(...) error {
    // format check; run five package commands in CPU-bounded batches
}

Local·CI는 저장소와 gofmt를 확인한 뒤 10개 command를 병렬 실행하고, 성공하면 coverage policy를 평가합니다. CI는 유효 base를 coverage에만 전달합니다. 별도 `mutation` subcommand는 `runMutation`을 통해 다섯 package를 worker 1개씩 CPU batch로 실행합니다.

실제 command 실행은 주입된 runner가 맡는다

// tools/verify/runner.go:89-100
if err := runConcurrent(ctx, root, parallelCommands, runner); err != nil {
    return fmt.Errorf("verification stopped during parallel checks: %w", err)
}
if err := runner(ctx, root, coverageCommand); err != nil {
    return fmt.Errorf("verification stopped after %s: %w",
        formatCommand(coverageCommand), err)
}

commandRunner 주입으로 production에서는 실제 process를 실행하고, runner test에서는 local·CI command 집합, 병렬 실패 취소와 coverage 단계의 실행 조건을 검증합니다.

병렬 실패 처리

runConcurrent는 실패 뒤 peer command 취소를 요청하고 종료를 기다립니다. 취소되지 않은 실패를 함께 반환하며, 이 단계가 실패하면 coverage policy command는 시작하지 않습니다.

04 · command graph

local·CI 10개 병렬 command 뒤 coverage policy를 평가한다

아래 10개 command는 local·CI의 공통 병렬 단계다. CI coverage는 유효 `GOMAXPROCS`만큼 parallel하며 `--base`는 coverage command에만 전달한다. Mutation은 자동 gate에 없고, `go run ./tools/verify mutation`으로 별도 실행한다. Runner test는 두 자동 gate에 mutation이 없는지, 수동 command가 다섯 package를 선택하는지 확인한다.

01 · parallel

go vet ./...

비정상적인 코드 패턴을 정적으로 검사합니다.

02 · parallel

go run ./tools/verify traceability

source metadata, MQTT matrix와 requirement union이 일치하는지 검사합니다.

03 · parallel

go run ./tools/verify architecture

production import graph가 Clean Architecture 경계를 지키는지 확인합니다.

04 · parallel

go test ./... + atomic profile

전체 package test를 실행하고 `.artifacts/verification/coverage.out`을 만듭니다.

05 · parallel

go test -race ./cmd/... ./internal/... -count=1

production packages의 data race를 검사합니다.

06 · parallel fuzz

MQTT FuzzDecoder

malformed frame의 panic·정의되지 않은 오류를 검사합니다.

07 · parallel fuzz

MQTT FuzzCodecRoundTrip

성공한 packet codec round-trip이 packet 의미를 보존하는지 확인합니다.

08 · parallel fuzz

routing FuzzTopicMatching

09 · parallel fuzz

10 · parallel fuzz

11 · after parallel

go run ./tools/verify coverage ...

floor·ratchet를 평가하고 `coverage-summary.json`을 남깁니다; CI에서는 diff coverage도 평가합니다.

05 · bounded fuzz

fuzz gate는 무한 탐색이 아니라 고정 quota와 보존된 실패 입력이다

Go fuzz는 seed와 과거 corpus에서 시작해 입력을 변형합니다. 현재 gate는 각 target을 별도 process로 실행하고 -fuzztime=10000x, -parallel=1을 사용합니다. 실행 순서 자체는 deterministic하지 않으므로, 반복 계약은 “같은 입력 순서”가 아니라 “같은 quota와 failure corpus 보존”입니다.

target입력·경계관찰 가능한 invariant
FuzzDecoderraw frame bytes, protocol selectorpanic 금지, malformed input에서 partial consumption 금지, 정의된 codec error
FuzzCodecRoundTripdecoder가 성공시킨 packetencode→decode 뒤 packet semantics 보존
FuzzTopicMatchingraw filter/topic/QoSwildcard·system topic·invalid sentinel·table state·effective QoS
FuzzLifecycleTransitionsprotocol, Clean Start, expiry selector, 1..86400초 finite intervalconnected state, duplicate/identity error, retention, exact expiry, Session Present
 
go test ./internal/domain/mqtt -run=^$ -fuzz=^FuzzDecoder$ -fuzztime=10000x -parallel=1
go test ./internal/domain/mqtt -run=^$ -fuzz=^FuzzCodecRoundTrip$ -fuzztime=10000x -parallel=1
go test ./internal/domain/routing -run=^$ -fuzz=^FuzzTopicMatching$ -fuzztime=10000x -parallel=1
go test ./internal/domain/session -run=^$ -fuzz=^FuzzLifecycleTransitions$ -fuzztime=10000x -parallel=1

실패 입력의 다음 위치

Go가 발견한 재현 가능한 failure는 해당 package의 testdata/fuzz/<Target>/ corpus로 승격합니다. 그러면 ordinary test에서도 같은 실패를 확인할 수 있습니다.

무엇을 보장하지 않는가

10000x는 모든 가능한 MQTT 입력을 탐색한다는 뜻이 아닙니다. 고정 작업량 안에서 invariant를 반복 확인하는 bounded campaign입니다.

06 · mutation

mutation은 test가 실제 규칙의 변화를 잡는지 확인한다

Mutation testing은 production 조건을 일부러 바꿔 test assertion의 검출력을 확인합니다. `local`과 `ci`는 mutation을 실행하지 않습니다. 개발자는 저장소 루트에서 go run ./tools/verify mutation을 실행해 Delivery·MQTT·NodeDrain·Security·Session을 검사할 수 있습니다. Runner는 worker 1개씩 CPU 예산에 맞춰 package 작업을 batch로 실행합니다. KILLED는 test 실패, LIVED는 test 통과, NOT_COVERED는 해당 코드가 실행되지 않음을 뜻합니다. TIMED OUT은 kill로 계산하지 않습니다.

다섯 package 점수는 합산하지 않습니다. 각 package 결과를 별도 JSON에 저장하므로 한 package의 강한 test가 다른 package의 약한 state machine을 숨기지 않습니다.

정책과 대상: gremlins.yaml, delivery/state.go, mqtt/framing.go, nodedrain/drain.go, security/security.go, session/state.go.

07 · coverage와 CI

coverage는 실행 profile과 정책 평가를 두 단계로 나눈다

runner의 10번째 command는 atomic coverprofile을 생성하고, 11번째 command는 그 profile을 읽어 정책을 평가합니다. profile 생성과 정책 판정을 나누면 “test process가 profile을 만들었는가”와 “그 profile이 기준을 넘었는가”를 서로 다른 실패로 볼 수 있습니다. 

// tools/verify/runner.go:71-80
// 10. profile 생성
 go test ./cmd/... ./internal/... ./tests/integration/... \
   -count=1 -covermode=atomic \
   -coverpkg=./cmd/...,./internal/... \
   -coverprofile=.artifacts/verification/coverage.out

// 11. profile 정책 평가
 go run ./tools/verify coverage \
   --profile .artifacts/verification/coverage.out \
   --policy tests/verification/coverage-policy.json \
   --report .artifacts/verification/coverage-summary.json

// CI일 때만 위 coverage command 뒤에 --base HEAD~1 추가
정책 층현재 기준설정 위치
전체 productionline 85% / function 90%overallFloor
core packageline/function 95%coreFloor·corePackages
PR diffline/function/branch 80%diffFloor
ratchet정책 파일의 명시값이며 측정치만으로 자동 변경하지 않음ratchet

CI base 전달의 의미

runCI는 빈 base를 거절합니다. 유효한 base는 coverage command에만 전달합니다. Mutation은 CI command 목록에 없으며, 별도 수동 명령은 diff base를 받지 않습니다.

현재 branch coverage

승인된 branch instrumentation이 고정되기 전까지 branch coverage는 not_evaluated와 이유를 artifact에 기록합니다. line coverage로 대신하지 않습니다.

08 · 계약과 실패

runner tests fix command counts, parallel cancellation and base propagation

`TestRunLocalOmitsMutationChecksAndCoverageWithoutBase`는 local에서 mutation과 `--base`를 제외하는지 확인합니다. `TestRunCIRequiresBaseAndPropagatesBaseToCoverage`는 CI 12개 command와 coverage-only base를 확인합니다. `TestRunMutationExecutesAllPackagesWithOneGremlinsWorker`는 수동 명령의 다섯 package를 검사하고, `TestMutationCommandConcurrencyUsesAvailableCPU`는 package batch 크기를 확인합니다. 

// tools/verify/runner_test.go:109-128
err := runConcurrent(context.Background(), ".", []commandSpec{
    {Name: "go", Args: []string{"fail"}},
    {Name: "go", Args: []string{"wait"}},
}, runner)
if !errors.Is(err, failure) {
    t.Fatalf("runConcurrent() error = %v, want original failure", err)
}

Runner test는 local·CI의 12개 command와 mutation 제외를 비교합니다. 수동 mutation test는 다섯 package와 `workers=1`을 확인합니다. CPU batch 경계와 병렬 실패 취소도 별도 시험으로 확인합니다.

09 · 증거와 범위

수동 mutation 검사 범위

수동 명령은 delivery·mqtt·nodedrain·security·session의 다섯 package를 확인합니다. 전달·프로토콜·드레인·ACL·소유권 상태 머신 범위를 package별로 검사합니다. 각 package의 efficacy와 mutant coverage는 모두 80% 이상이어야 합니다.

현재 작업 트리에서 다시 실행할 명령

go run ./tools/verify local
go run ./tools/verify ci --base HEAD~1
go run ./tools/verify mutation

수동 mutation 명령은 Gremlins를 실행하고 JSON artifact를 만듭니다. `local`과 `ci`는 mutation artifact를 만들지 않습니다. HTML 문서를 여는 것 자체는 검증 실행이 아니므로, release evidence에는 실제 command output과 artifact를 별도로 보존해야 합니다.
