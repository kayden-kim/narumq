NaruMQ / 코드로 읽는 검증 게이트

코드 변경이 `PASS`가 되기까지

이 문서는 NaruMQ의 현재 local·CI verification gate를 명령 목록으로만 나열하지 않습니다. 개발자가 실행한 한 줄의 입력이 runner의 상태와 13개 command를 거쳐 fuzz·race·traceability·architecture·coverage·mutation 증거와 최종 종료 상태가 되는 과정을 실제 코드와 기준 문서에 연결해 설명합니다.

01 · 결과부터

게이트의 결과는 숫자 하나가 아니라, 재현 가능한 증거 묶음이다

개발자는 저장소 루트에서 go run ./tools/verify local을 실행합니다. CI에서는 여기에 diff coverage의 기준 ref를 더해 go run ./tools/verify ci --base <merge-base>를 실행합니다. 두 진입점은 같은 command graph를 사용하고, CI의 차이는 coverage command에만 --base를 전달하는 것입니다.

성공의 의미

모든 command가 exit code 0으로 끝났고, 각 gate가 요구하는 artifact를 만들었다는 뜻입니다. 하나의 평균 점수가 모든 품질을 대신하지 않습니다.

실패의 의미

runner는 실패한 command의 이름을 감싸 반환하고 그 뒤 단계는 실행하지 않습니다. 따라서 “어디까지 확인됐는가”가 로그 순서에 남습니다.

혼동하면 안 되는 것

coverage 숫자가 높아도 traceability나 mutation이 실패하면 gate는 닫히지 않습니다. 각 검사는 서로 다른 종류의 누락을 찾습니다.

02 · 배경 개념

각 검사는 서로 다른 질문에 답한다

verification gate는 같은 코드를 여러 번 실행하는 과정이 아닙니다. 정상 입력, 비정상 입력, 동시성, 요구사항 연결, package 경계, 실행되지 않은 코드와 약한 assertion을 서로 다른 방법으로 확인합니다.

검사쉬운 질문현재 gate가 확인하는 것
unit정상·오류·경계 입력에서 결과가 맞는가?전체 package test를 한 번 실행합니다.
fuzz사람이 고른 예시 밖의 입력에서도 invariant가 깨지지 않는가?MQTT codec 2개, routing 1개, session 1개를 고정 quota로 실행합니다.
race동시에 접근할 때 data race가 생기지 않는가?전체 package를 race detector로 다시 실행합니다.
traceability지원한다고 선언한 규격·요구사항에 실제 test가 연결됐는가?source의 `Traceability` metadata와 conformance matrix를 양방향 비교합니다.
architecturepackage가 허용되지 않은 방향으로 의존하지 않는가?현재 `go list` import graph를 domain·application·adapter 경계와 비교합니다.
coverage실행 가능한 production code가 실제로 실행됐는가?atomic coverprofile과 policy floor·ratchet·CI diff를 평가합니다.
mutationtest assertion이 production 조건의 변화를 실제로 잡는가?delivery/session state machine mutant를 package별로 변형해 실행합니다.
이 구분이 필요한 이유는 “실행됐다”와 “검증됐다”가 다르기 때문입니다. 예를 들어 line coverage는 한 줄이 실행됐다는 사실을 보여주지만, 그 줄의 조건을 반대로 바꿨을 때 test가 실패하는지는 mutation이 확인합니다.
03 · runner 흐름

입력은 `main.go`에서 시작하고, 실제 순서는 `runVerification`이 소유한다

`tools/verify/main.go`는 subcommand를 고릅니다. `local`은 runLocal, `ci`는 base ref를 먼저 확인한 뒤 runCI를 호출합니다. 두 함수는 공통 함수인 `runVerification`으로 들어가므로 local과 CI 사이에서 command 순서가 갈라지지 않습니다. 

// tools/verify/runner.go:40-56
func runLocal(ctx context.Context, root string, runner commandRunner) error {
    return runVerification(ctx, root, verificationOptions{}, runner)
}

func runCI(ctx context.Context, root, base string, runner commandRunner) error {
    if strings.TrimSpace(base) == "" {
        return fmt.Errorf("ci requires --base <git-ref>")
    }
    return runVerification(ctx, root, verificationOptions{CI: true, Base: base}, runner)
}

func runVerification(...) error {
    ensureRepositoryRoot(root)
    checkGoFormat(root)
    os.MkdirAll(".artifacts/verification", 0o755)
    // 아래 commandSpec 배열을 순서대로 실행한다.
}

사전 단계는 아직 외부 command를 실행하지 않습니다. `ensureRepositoryRoot`는 module path가 narumq인지 확인하고, `checkGoFormat`은 Go source를 수정하지 않고 포맷 불일치만 보고합니다. 이 단계가 실패하면 13개 command는 시작되지 않습니다.

실제 command 실행은 주입된 runner가 맡는다

// tools/verify/runner.go:82-102
for _, command := range commands {
    if err := runner(ctx, root, command); err != nil {
        return fmt.Errorf("verification stopped after %s: %w",
            formatCommand(command), err)
    }
}

// 실제 실행에서는 executeCommand가 exec.CommandContext로
// command.Name과 command.Args를 실행하고 exit code를 보존한다.

commandRunner를 함수 타입으로 분리했기 때문에 production에서는 실제 process를 실행하고, runner test에서는 command를 기록하는 가짜 함수를 넣을 수 있습니다. 이 seam은 검증 대상이 business logic이 아니라 “순서와 중단 계약”임을 드러냅니다.

첫 실패 중단

예를 들어 unit command가 실패하면 fuzz·race·coverage·mutation은 실행되지 않습니다. 로그에 실패 command가 포함되므로 뒤 단계가 실행됐다고 추정하지 않아도 됩니다.

04 · 고정된 순서

13개 command는 빠른 피드백에서 비싼 gate로 진행한다

앞 단계는 컴파일·기본 동작·입력 안정성을 빠르게 확인하고, 뒤 단계는 race·coverage·mutation처럼 더 오래 걸리거나 artifact를 필요로 하는 검사를 수행합니다. 이 순서는 `TestRunCIRequiresBaseAndPropagatesBaseToCoverage`에서 전체 `Name`·`Args` 목록으로 고정되어 있습니다.

01 · vet

go vet ./...

컴파일 가능한 코드에서 정적 분석 경고를 찾습니다.

02 · unit

go test ./... -count=1

test cache를 사용하지 않고 전체 package test를 실행합니다.

03 · fuzz

MQTT FuzzDecoder

malformed frame이 panic하거나 정의되지 않은 error를 만들지 않는지 확인합니다.

04 · fuzz

MQTT FuzzCodecRoundTrip

성공한 packet codec round-trip이 packet 의미를 바꾸지 않는지 확인합니다.

05 · fuzz

routing FuzzTopicMatching

filter·topic validation과 독립 oracle 기반 match·QoS invariant를 확인합니다.

06 · fuzz

session FuzzLifecycleTransitions

07 · race

08 · trace

09 · graph

10 · profile

production package와 integration test를 .artifacts/verification/coverage.out에 기록합니다.

11 · policy

go run ./tools/verify coverage ...

floor·ratchet·diff coverage를 평가하고 coverage-summary.json을 남깁니다.

12 · mutation

13 · mutation

05 · bounded fuzz

fuzz gate는 무한 탐색이 아니라 고정 quota와 보존된 실패 입력이다

Go fuzz는 seed와 과거 corpus에서 시작해 입력을 변형합니다. 현재 gate는 각 target을 별도 process로 실행하고 -fuzztime=10000x, -parallel=1을 사용합니다. 실행 순서 자체는 deterministic하지 않으므로, 반복 계약은 “같은 입력 순서”가 아니라 “같은 quota와 failure corpus 보존”입니다.

target입력·경계관찰 가능한 invariant
FuzzDecoderraw frame bytes, protocol selectorpanic 금지, malformed input에서 partial consumption 금지, 정의된 codec error
FuzzCodecRoundTripdecoder가 성공시킨 packetencode→decode 뒤 packet semantics 보존
FuzzTopicMatchingraw filter/topic/QoSwildcard·system topic·invalid sentinel·table state·effective QoS
FuzzLifecycleTransitionsprotocol, Clean Start, expiry selector, 1..86400초 finite intervalconnected state, duplicate/identity error, retention, exact expiry, Session Present
 
go test ./internal/domain/mqtt -run=^$ -fuzz=^FuzzDecoder$ -fuzztime=10000x -parallel=1
go test ./internal/domain/mqtt -run=^$ -fuzz=^FuzzCodecRoundTrip$ -fuzztime=10000x -parallel=1
go test ./internal/domain/routing -run=^$ -fuzz=^FuzzTopicMatching$ -fuzztime=10000x -parallel=1
go test ./internal/domain/session -run=^$ -fuzz=^FuzzLifecycleTransitions$ -fuzztime=10000x -parallel=1

실패 입력의 다음 위치

Go가 발견한 재현 가능한 failure는 해당 package의 testdata/fuzz/<Target>/ corpus로 승격합니다. 그러면 ordinary test에서도 같은 실패를 확인할 수 있습니다.

무엇을 보장하지 않는가

10000x는 모든 가능한 MQTT 입력을 탐색한다는 뜻이 아닙니다. 고정 작업량 안에서 invariant를 반복 확인하는 bounded campaign입니다.

06 · mutation

mutation은 test가 실제 규칙의 변화를 잡는지 확인한다

mutation testing은 production 조건을 일부러 바꿉니다. 예를 들어 조건의 부정을 뒤집거나 경계 비교를 바꾼 뒤 기존 test를 실행합니다. test가 실패하면 mutant는 KILLED, 계속 통과하면 LIVED, 해당 코드가 실행되지 않으면 NOT_COVERED입니다.

delivery와 session은 점수를 합산하지 않습니다. 한 package의 강한 test가 다른 package의 약한 state machine을 숨기지 않도록 command와 JSON을 분리합니다. 

go tool gremlins unleash --config=tests/verification/gremlins.yaml --output=.artifacts/verification/mutation-delivery.json internal/domain/delivery
go tool gremlins unleash --config=tests/verification/gremlins.yaml --output=.artifacts/verification/mutation-session.json internal/domain/session

정책과 대상: gremlins.yaml, delivery/state.go, session/state.go.

07 · coverage와 CI

coverage는 실행 profile과 정책 평가를 두 단계로 나눈다

runner의 10번째 command는 atomic coverprofile을 생성하고, 11번째 command는 그 profile을 읽어 정책을 평가합니다. profile 생성과 정책 판정을 나누면 “test process가 profile을 만들었는가”와 “그 profile이 기준을 넘었는가”를 서로 다른 실패로 볼 수 있습니다. 

// tools/verify/runner.go:71-80
// 10. profile 생성
 go test ./cmd/... ./internal/... ./tests/integration/... \
   -count=1 -covermode=atomic \
   -coverpkg=./cmd/...,./internal/... \
   -coverprofile=.artifacts/verification/coverage.out

// 11. profile 정책 평가
 go run ./tools/verify coverage \
   --profile .artifacts/verification/coverage.out \
   --policy tests/verification/coverage-policy.json \
   --report .artifacts/verification/coverage-summary.json

// CI일 때만 위 coverage command 뒤에 --base HEAD~1 추가
정책 층현재 기준설정 위치
전체 productionline/function 90%overallFloor
core packageline/function 95%coreFloor·corePackages
PR diffline/function 95%diffFloor
ratchet정책 파일의 명시값이며 측정치만으로 자동 변경하지 않음ratchet

CI base 전달의 의미

runCI는 빈 base를 거절합니다. 유효한 base를 받으면 runner test가 전체 command 목록을 비교해 --base HEAD~1이 coverage command에 정확히 한 번만 있는지 확인합니다. fuzz·race·mutation command에는 diff base를 넣지 않습니다.

현재 branch coverage

승인된 branch instrumentation이 고정되기 전까지 branch coverage는 not_evaluated와 이유를 artifact에 기록합니다. line coverage로 대신하지 않습니다.

08 · 계약과 실패

runner test가 순서·중단·base 전달을 실행 계약으로 고정한다

`TestRunLocalExecutesOrderedCommandsAndStopsAtFirstFailure`는 두 번째 command에서 가짜 실패를 반환합니다. 기대 결과는 첫 번째 go vet와 두 번째 unit test만 실행되고, fuzz 이후 단계는 실행되지 않는 것입니다. 

// tools/verify/runner_test.go:18-35
runner := func(_ context.Context, _ string, spec commandSpec) error {
    commands = append(commands, formatCommand(spec))
    if len(commands) == 2 {
        return failure
    }
    return nil
}

// 결과: len(commands)==2
// commands[0] = go vet ./...
// commands[1] = go test ./... -count=1

성공 경로는 13개 commandSpec의 이름과 인자를 exact comparison합니다. 이 검사가 없으면 command를 하나 추가하거나 base를 잘못된 단계에 전달해도 package test 자체는 통과할 수 있습니다.

실패 위치runner의 반응뒤 단계
repository rootmodule path 오류 반환실행하지 않음
gofmt prechecksource를 바꾸지 않고 파일 목록 반환실행하지 않음
unit·fuzz·race실패 command와 exit code를 wrapping실행하지 않음
traceability·architecture정책 위반을 command 실패로 전달coverage·mutation 실행하지 않음
coverage·mutationartifact와 함께 gate 실패이미 끝난 앞 단계는 유지
현재 runner는 mutation JSON을 다시 읽어 점수를 계산하지 않습니다. Gremlins가 config threshold를 적용하고 exit code를 반환하며, runner는 그 process 결과와 JSON artifact를 보존합니다. 따라서 score를 볼 때는 package별 JSON을 직접 확인해야 합니다.
09 · 증거와 범위

PASS를 설명할 때는 실행 명령과 artifact를 함께 남긴다

표준 artifact

  • .artifacts/verification/coverage.out — atomic raw profile
  • .artifacts/verification/coverage-summary.json — floor·ratchet·diff 평가
  • .artifacts/verification/mutation-delivery.json — delivery mutation 결과
  • .artifacts/verification/mutation-session.json — session mutation 결과
  • internal/domain/*/testdata/fuzz/<Target>/ — 발견된 failure corpus

현재 Phase 0의 범위

mutation 대상은 delivery/session state machine입니다. production ownership·ACL·drain state machine은 아직 현재 capability가 아니므로 gate 대상에 포함하지 않습니다. 해당 기능이 구현되면 package별 command와 80% 기준을 같은 변경에 추가해야 합니다.

현재 작업 트리에서 다시 실행할 명령

go run ./tools/verify local
go run ./tools/verify ci --base HEAD~1

이 두 명령이 성공하려면 코드, source traceability metadata, conformance matrix, coverage policy, Gremlins config와 test corpus가 서로 같은 계약을 가져야 합니다. HTML을 읽는 것 자체는 검증 실행이 아니므로, release evidence에는 실제 command output과 artifact를 별도로 보존해야 합니다.
