NaruMQ / 코드로 읽는 MQTT

네트워크 바이트가 검증된 메시지와 세션 상태가 되기까지

이 문서는 MQTT 패킷을 읽고 쓰는 코드만 따로 설명하지 않습니다. 연결 요청이 들어와 세션이 열리고, subscription option이 보존되고, standalone retained publication이 bounded memory를 갱신하거나 dynamic cluster retained publication이 tenant별 Raft state에 commit되고, 발행 메시지가 맞는 구독자의 제한된 큐에 들어간 뒤 MQTT 응답 바이트가 나가는 흐름을 실제 코드, standalone loopback TCP, cluster process acceptance에 연결합니다.

01 · 결과부터

무엇이 달라졌는가

클라이언트가 TCP 연결로 CONNECT 또는 PUBLISH 바이트를 보내면, NaruMQ는 먼저 길이와 고정 헤더를 확인합니다. 그 다음 바이트를 그대로 전달하지 않고, 검증이 끝난 mqtt.Connect, mqtt.Publish 같은 값으로 바꿉니다. 이 값은 세션, 구독표, 전달 큐라는 각각의 책임 있는 경계를 통과합니다.

예시: 연결 요청

입력에 MQTT 3.1.1 CONNECT가 오면 프로토콜 이름과 버전, 플래그, Client ID를 확인합니다. 성공하면 세션을 열고 CONNACK를 보냅니다.

같은 Client ID가 이미 연결되어 있거나 지원하지 않는 자격 증명·Will 상태이면 연결을 조용히 무시하지 않고 거절 응답을 만듭니다.

예시: 발행 요청

sensor/room1에 QoS 0 메시지가 오면 유효한 구독 필터와 비교합니다. 일치한 각 세션의 큐에 독립된 payload 복사본을 넣고, 연결의 쓰기 루프를 깨웁니다.

큐가 가득 찬 세션은 성공으로 숨기지 않고 Saturated 결과로 분류한 뒤 현재 TCP 경계에서 연결을 닫습니다.

영속 세션은 연결이 닫혀도 큐의 offline FIFO와 완료되지 않은 QoS 1·2 outbound 상태를 process-local memory에 남깁니다. 재연결에서는 CONNACK를 먼저 보낸 뒤 저장된 Packet ID와 상태로 recovery packet을 출력합니다.

읽을 때 먼저 기억할 한계

패킷 코덱과 QoS 1·2 상태 머신은 internal/domain/delivery에서 단위 테스트 가능한 정책으로 구현되고, 현재 개발용 TCP 경로도 ingress·outbound QoS 0·1·2 handshake를 연결합니다.

Message Expiry는 수신 시각에서 absolute deadline을 만들고 queue·retained replay·writer 출력에 적용합니다. MQTT 3.1.1에는 expiry property를 쓰지 않지만 만료 판정은 유지합니다.

실제 연결 시작점

tcp.NewServer는 리스너, 디코더, 인코더, connect·subscribe·publish 응용 기능, 전달 큐를 주입받습니다. 서버는 이 객체들을 직접 새로 만들지 않으므로, 조립 책임은 cmd/narumq에 남습니다.

connection.readLoop는 읽은 바이트를 누적하고, 한 버퍼에 여러 패킷이 들어오거나 패킷이 나뉘어 들어오는 경우를 처리합니다. 성공한 패킷만 앞에서부터 제거하고, 불완전한 패킷이면 다음 읽기를 기다립니다.

응용 포트가 필요한 이유

publish.UseCase는 큐의 구체 구현을 모르고 TryEnqueue라는 약속만 사용합니다. 메모리 큐는 그 약속의 한 구현입니다.

이렇게 하면 정책은 “가득 찼을 때 무엇으로 분류할지”를 결정하고, 저장 방식은 “어떻게 보관할지”만 결정합니다.

04 · 패킷 경계와 코덱

먼저 길이를 믿을 수 있게 만든 다음, 본문을 의미 있는 값으로 바꾼다

MQTT 패킷은 첫 바이트의 종류와 플래그, 이어지는 남은 길이(Remaining Length), 그 길이만큼의 본문으로 구성됩니다. 남은 길이는 7비트 숫자를 여러 바이트에 나누어 저장하는 형식입니다. framing.go는 네 바이트를 넘는 표현과 불필요하게 긴 표현을 거부하고, 설정된 최대 크기도 적용합니다. 

// internal/domain/mqtt/decoder.go:19-47
// 설명을 위해 핵심 흐름만 남긴 단순화한 발췌다.
func (d *Decoder) Decode(src []byte, version ProtocolVersion) (Packet, int, error) {
    packetType := PacketType(src[0] >> 4)
    flags := src[0] & 0x0F
    if err := validateFixedHeader(packetType, flags); err != nil { return nil, 0, err }

    remainingLength, lengthBytes, err := decodeVariableByteInteger(src[1:])
    if err != nil { return nil, 0, err }
    if remainingLength > d.maxPacketSize { return nil, 0, ErrPacketTooLarge }

    frameHeaderLength := 1 + lengthBytes
    if remainingLength > len(src)-frameHeaderLength {
        return nil, 0, ErrIncompletePacket
    }
    body := src[frameHeaderLength : frameHeaderLength+remainingLength]
    // packet 종류에 따라 decodeConnect, decodePublish 등을 호출한다.
}

반환하는 세 번째 값이 오류이면 두 번째 값은 항상 0입니다. 그래서 호출자는 실패한 바이트를 버리지 않고, ErrIncompletePacket이면 더 읽고, 그 밖의 오류이면 프로토콜 오류로 닫을 수 있습니다. 성공하면 consumed만큼만 제거하므로 한 번의 읽기에 붙어 온 다음 패킷도 잃지 않습니다.

입력 버퍼 소유권

디코더는 호출자의 입력 버퍼를 잠깐 빌려 읽습니다. 반환된 payload·password·will 데이터는 cloneBytes로 복사되어 패킷 값이 자기 데이터를 소유합니다.

따라서 TCP 읽기 루프가 다음 패킷을 위해 앞부분을 이동해도, 이미 만든 mqtt.Publish의 payload가 바뀌지 않습니다.

출력은 원자적으로 실패한다

// internal/domain/mqtt/encoder.go:18-33, 171-178
// 실제 구현의 핵심 발췌다. 나머지 packet case와 주변 변수 선언은 생략했다.
switch value := packet.(type) {
case Connect:
    body, err = encodeConnect(value, e.maxPacketSize)
case Publish:
    body, err = encodePublish(value, e.maxPacketSize)
// ACK·구독·제어 패킷도 같은 방식으로 선택한다.
}
if err != nil { return dst, err }
dst = append(dst, byte(packetType<<4)|flags)
dst = appendVariableByteInteger(dst, len(body))
dst = append(dst, body...)
return dst, nil

실제 구현은 먼저 본문을 검증하고 만든 뒤, 고정 헤더와 남은 길이를 붙입니다. 잘못된 패킷이 일부만 출력되는 일을 막는 순서입니다.

검사되는 실패 예

  • 고정 헤더 플래그가 패킷 종류와 맞지 않음
  • 최대 Remaining Length 초과
  • QoS 0인데 DUP 또는 Packet ID 사용
  • 빈 토픽, 와일드카드가 들어간 Topic Name
  • 0인 Packet ID, 잘못된 UTF-8, 지원하지 않는 버전
  • MQTT 5 Message Expiry property, absolute deadline ownership와 remaining interval 계산
05 · CONNECT에서 세션까지

패킷 검증과 실제 연결 허용은 서로 다른 층이다

decodeConnect는 MQTT 3.1.1·5.0의 프로토콜 이름과 버전, Clean Start, Keep Alive, Client ID, 선택 필드를 읽습니다. MQTT 5에서는 Session Expiry Interval도 읽습니다. 이것은 “바이트가 규격에 맞는가”를 확인하는 일입니다. 

// internal/domain/mqtt/connect.go:183-189
// 설명을 위해 함수의 검증·크기 확인 부분만 남긴 단순화한 발췌다.
func encodeConnect(connect Connect, maxPacketSize int) ([]byte, error) {
    bodySize, err := validateConnect(connect)
    if err != nil { return nil, err }
    if bodySize > maxPacketSize { return nil, ErrPacketTooLarge }
    // 이후 실제 구현은 body를 만들고 반환한다.
}

그 다음 connect.UseCase.Connect가 개발용 브로커 정책을 적용합니다. 현재 구현은 Client ID가 비어 있거나 username·password·Will이 있으면 거절 CONNACK를 돌려줍니다. 코덱이 해당 필드를 읽을 수 있다는 것과 이 개발용 실행 경로가 그 기능을 허용한다는 것은 다른 계약입니다.

06 · 구독 라우팅, retained message와 제한된 큐

옵션을 보존하고 한 번 매칭한 뒤, retained replay는 route commit 전에 원자적으로 예약한다

구독 필터는 메시지를 받을 토픽의 모양입니다. +는 한 단계, #는 마지막에서 여러 단계를 뜻합니다. ValidateTopicFilter는 와일드카드 위치와 MQTT 문자열 규칙을 확인하고, 현재 단계에서는 $share/... 공유 구독도 group별로 지원합니다. 각 exact filter의 NoLocal, RetainAsPublished와 RetainHandling은 routing·subscribe 경계에서 보존됩니다.

    publishQoS mqtt.QoS,
    publishedRetain bool,

같은 세션이 sensors/+와 sensors/room1을 동시에 구독해도 한 번만 받습니다. Established delivery의 RETAIN은 RAP에 따라 달라지지만, SUBSCRIBE가 발생시킨 retained replay는 항상 RETAIN=1입니다.

Retained replace/delete와 replay

// internal/application/publish/publish.go
expiresAt := time.Time{}
if packet.HasMessageExpiryInterval {
    expiresAt = receivedAt.Add(time.Duration(packet.MessageExpiryInterval) * time.Second)
}
now := useCase.clock.Now()
expired := !expiresAt.IsZero() && !now.Before(expiresAt)
if packet.Retain {
    tenantID := useCase.routes.SessionTenant(publisherSessionID)
    deleteValue := len(packet.Payload) == 0 || expired
    message := retained.MessageDTO{
        TenantID: tenantID, PublisherSessionID: publisherSessionID, Topic: packet.Topic,
    }
    if !deleteValue {
        message.Payload = packet.Payload
        message.QoS = packet.QoS
        message.ExpiresAt = expiresAt
    }
    if useCase.retainedCommitter != nil {
        // Raft commit and node-local projection update happen before routing.
        err = useCase.retainedCommitter.CommitRetained(context.Background(),
            RetainedChangeDTO{Message: message, Delete: deleteValue, ProposedAt: now})
    } else if deleteValue {
        err = useCase.retained.Delete(tenantID, packet.Topic)
    } else {
        err = useCase.retained.Replace(message, now)
    }
    if err != nil {
        return ResultDTO{}, err
    }
}
if expired {
    return ResultDTO{}, nil
}
matches, err := useCase.routes.Match(publisherSessionID, packet.Topic, packet.QoS, packet.Retain)
// Successful retained state change precedes route matching/live fan-out.

// internal/application/subscribe/subscribe.go
queue.TryEnqueueBatch(replay, now)
routes.Subscribe(sessionID, subscription) // replay batch committed first

Retained key는 (tenantId, exact Topic Name)입니다. Standalone에서는 bounded memory repository가 authority이고, dynamic cluster에서는 RetainedCommitter가 mutation을 Raft에 commit합니다. Publisher node는 committed command를 local apply하고 replay projection을 갱신한 뒤 route matching과 live fan-out을 시작합니다. 다른 node는 각자 committed command를 apply하거나 snapshot catch-up할 때 local projection을 갱신합니다. Publish 완료가 모든 peer projection의 갱신 완료를 보장하지는 않습니다. Standalone repository와 cluster replay projection은 List(now)에서 now >= ExpiresAt인 값을 제거합니다. Raft 권위 state는 다음 retained command를 apply할 때 proposal 시각으로 만료 값을 결정적으로 제거하므로, 그 전에는 만료 entry가 snapshot/archive와 용량 한도에 남을 수 있습니다. Replay queue가 가득 차면 route를 만들지 않고 MQTT version에 맞는 실패 reason을 반환합니다.

영속 세션의 queued delivery와 outbound Packet ID 상태도 같은 application-owned queue에 보관됩니다. persistent disconnect에서는 삭제하지 않고, Clean Start 또는 Session Expiry가 실제 세션을 제거할 때만 함께 제거합니다.

    // ErrFull/ErrUnavailable은 다른 session fan-out을 막지 않는다.
}

한 세션의 큐가 가득 차도 다른 세션을 계속 시도합니다. Cluster retained commit은 route matching/live fan-out보다 먼저 완료되어야 합니다. Commit error는 해당 publish call의 fan-out을 막고, timeout만으로 proposal이 반영되지 않았다고 단정할 수는 없습니다.

메모리 경계

TryEnqueue와 TryEnqueueBatch는 payload를 복사하고 batch 전체를 수용할 수 없으면 아무것도 추가하지 않습니다.

retained.Repository는 전체 tenant에 걸친 entry 수와 tenant/topic/payload/publisher-routing-ID bytes 합계로 제한됩니다. 별도 tenant별 quota가 아니라 standalone authority이자 cluster replay projection입니다.

같은 메모리 adapter가 Packet ID별 QoS 1·2 상태도 보관합니다. PromoteHead는 FIFO head를 outbound 상태로 원자적으로 옮기고, ACK dispatcher는 ReplaceOutbound·CompleteOutbound로 상태를 먼저 갱신한 뒤 다음 출력을 깨웁니다.

현재 TCP writer는 연결 활성화 시 복구된 outbound를 먼저 출력하고, 이후 Peek·PromoteHead로 FIFO head를 하나씩 예약합니다. 만료된 queued/PUBLISH-stage 항목은 버리고, await-PUBCOMP 상태의 PUBREL은 원래 publication deadline과 무관하게 재개합니다. MQTT 5에는 올림한 remaining interval을 쓰고 MQTT 3.1.1에는 expiry property를 생략합니다.
07 · QoS 1·2 상태 머신

ACK는 단순한 응답 문자열이 아니라, 다음에 허용되는 행동을 바꾸는 상태다

QoS는 메시지가 목적지에 도착했다는 의미를 어느 정도까지 확인할지 정하는 수준입니다. QoS 0은 확인 없이 한 번 보냅니다. QoS 1은 PUBACK를 받아야 교환을 완료합니다. QoS 2는 PUBREC → PUBREL → PUBCOMP 네 단계로 중복 전달을 더 엄격하게 다룹니다.

방향·수준처음 보낼 것다음 상태재연결·중복 시 행동
송신자 QoS 1PUBLISHPUBACK 대기완료 전이면 DUP=1 PUBLISH 재전송
송신자 QoS 2PUBLISHPUBREC 대기PUBREC 후 PUBREL, PUBCOMP까지 대기
수신자 QoS 1응용 전달을 먼저 수락 대기수락 후 PUBACK중복 PUBLISH에는 동일한 ACK 경로
수신자 QoS 2응용 수락 전 상태 보관PUBREC → PUBREL → 최종 수락 → PUBCOMP중복 PUBLISH/PUBREL을 현재 상태에 맞게 재응답
 
// internal/domain/delivery/state.go:53-66, 119-129
// 설명을 위해 상태 전환의 핵심만 남긴 단순화한 발췌다.
state, action, err := NewOutbound(publish)
// action.Send는 DUP=false PUBLISH
retry, err := state.Resume()
// 완료 전에는 DUP=true PUBLISH 또는 PUBREL

// inbound는 응용 수락이 끝난 뒤 ACK를 보낸다.
state, action, err = NewInbound(publish)
// QoS 1: action.Deliver + action.AwaitAcceptance
state, action, err = state.Accept()
// action.Send = PUBACK, action.Complete = true

Action은 상태 변화의 결과를 한 번에 나타냅니다. 보낼 패킷(Send), 응용에 넘길 메시지(Deliver), 저장·수락 장벽을 기다려야 하는지(AwaitAcceptance), 교환이 끝났는지(Complete)를 호출자가 해석합니다. 이 구조는 패킷을 보냈다는 사실만으로 “전달 완료”라고 잘못 판단하지 않게 합니다.

코덱과 상태의 연결

decodeAcknowledgement는 Packet ID와 MQTT 5 reason code를 검증해 PubAck, PubRec, PubRel, PubComp 값으로 만듭니다.

Outbound.Receive는 그 값이 현재 Packet ID와 상태에 맞는지 다시 확인합니다. 코덱 검증만 통과했다고 아무 ACK나 적용하지 않습니다.

현재 실행 경로와의 차이

QoS 상태 머신은 internal/domain/delivery에서 단위 테스트 가능한 정책으로 구현됐습니다. 현재 activate가 저장된 outbound를 읽고 writeRecoveredDeliveries가 CONNACK 뒤에 복구하며, dispatchPubAck·ACK dispatcher가 queue 상태를 write-through합니다.

Message Expiry는 상태 머신과 별도의 absolute deadline으로 관리됩니다. queued/PUBLISH-stage 상태는 deadline이 지나면 억제하지만, PUBREL 단계는 PUBCOMP까지 재개할 수 있습니다.

08 · 세션 수명

연결이 끊겼다고 세션이 언제나 사라지는 것은 아니다

세션은 현재 연결 자체와, 끊긴 뒤 잠시 남을 수 있는 Client ID 기반 상태를 함께 말합니다. session.Lifecycle은 연결 여부, 만료 정책, 만료 시각, 폐기 여부를 소유합니다. Disconnect는 persistent disconnect에서 delivery queue를 보존하고, clean reset 또는 실제 session expiry에서만 queue와 라우팅 구독을 삭제합니다.

Open
Client ID로 기존 상태 조회
→
Connected
큐 등록·CONNACK
→
Disconnect
즉시 삭제 또는 만료 예약
→
Expired
재연결 시 Session Present 불가

MQTT 3.1.1에서는 Clean Start가 아니면 이 구현이 영속 세션 의미를 사용합니다. MQTT 5에서는 Session Expiry Interval이 0이면 즉시, 최대 uint32 값이면 무기한, 그 사이 값이면 Disconnect 시각부터 초 단위로 보존합니다. 만료 판정은 now >= expiresAt 경계에서 참이 됩니다.

재연결의 중요한 순서

  1. 저장소에서 같은 Client ID의 Lifecycle을 읽습니다.
  2. session.Open이 Clean Start, 폐기, 만료, 연결 중 여부를 판단합니다.
  3. 재개 세션이면 기존 queue와 outbound Packet ID 상태를 보존한 채 queue를 등록합니다.
  4. CONNACK를 먼저 쓰고, 저장된 Packet ID·QoS 상태를 DUP PUBLISH 또는 PUBREL로 복구합니다.
  5. 복구가 끝난 뒤에만 새 FIFO delivery를 예약하고 출력합니다.

큐 등록에 실패하면 저장소를 이전 값으로 되돌리거나 새 세션을 삭제하려고 합니다. 이 되돌림은 “세션은 열렸다고 저장됐는데 전달 큐는 없는” 중간 상태를 줄입니다.

아직 상위 계층 책임인 것

session.Open은 이미 연결된 Lifecycle을 takeover하지 않습니다. 같은 Client ID 연결을 어떻게 끊고 새 소유자에게 넘길지는 TCP 서버와 더 높은 연결 소유권 정책에서 결정해야 합니다.

이 파일은 그 정책이 존재한다고 가정하지 않고, 현재 구현된 거절 결과만 반환합니다.

11 · 현재 범위와 다음 경계

구현된 것과 아직 연결되지 않은 것을 구분한다

이 slice로 확인되는 것

  • MQTT 3.1.1·5.0 패킷의 제한된 코덱과 오류 분류
  • CONNECT, CONNACK, PUBLISH, 구독·ACK·제어 패킷 값
  • 와일드카드 기반 비공유 구독 매칭과 session별 FIFO 큐
  • subscription option별 No Local·Retain As Published와 Retain Handling
  • Standalone은 QoS 0·1·2 ingress/outbound ACK 상태와 재전송을 지원하며 dynamic cluster MQTT ingress는 현재 QoS 0만 받습니다.
  • Tenant + exact topic별 retained replace/delete와 원자적 replay, standalone profile의 expiry purge
  • Dynamic cluster의 QoS 0 retained/offline Raft commit, node 간 replay, NMQBKUP3 archive/restore, restart와 learner catch-up
  • Message Expiry absolute deadline, remaining interval serialization과 MQTT version별 property 규칙
  • Clean Start, Session Expiry, Session Present 상태
  • 개발용 TCP ingress와 SUBACK-before-replay single writer 출력 순서
  • persistent session의 process-local offline FIFO와 미완료 QoS 1·2 outbound 재연결 복구

현재 문서와 코드가 명시하는 제한

  • Persistent offline queue와 미완료 QoS 1·2 outbound 복구는 process-local memory에 머무릅니다. Cluster는 offline delivery를 복제하지 않고 QoS 1·2 durable ACK를 제공하지 않습니다.
  • Retained cluster write는 정확히 같은 release/protocol/schema profile이 필요합니다. 이 gate는 N/N-1 rolling upgrade나 rollback 호환성을 입증하지 않습니다.
  • Message Expiry metadata는 MQTT 3.1.1 outbound wire에서 생략되지만 queued/PUBLISH-stage deadline은 적용
  • Persistent session/offline delivery의 영속 저장과 process 재시작 자동 복구는 retained cluster backup 경로와 별개입니다.
현재 제한은 실제 호출 관계에 근거합니다. Session/offline delivery 복구는 process-local memory에 한정되지만, retained state는 standalone memory 경로와 dynamic cluster Raft 경로로 나뉩니다. Cluster 경로는 tenant-scoped QoS 0 retained replication과 v2 backup만 증명하며, 일반 QoS 1·2 durable delivery를 포함하지 않습니다.
