NaruMQ · Phase 0 · Gate 4

alpha 한 줄이 세 노드에 안전하게 남는 과정

이 문서는 합의 알고리즘을 처음 보는 개발자가 “무슨 값이 어디로 가는가”를 놓치지 않도록 다시 구성했습니다. 명령 하나를 넣고, 기록에 남기고, 다른 노드에 전달하고, 한 노드를 껐다 켠 뒤에도 복구하는 흐름을 같은 예시로 끝까지 따라갑니다.

고정 voter: node 1 · 2 · 3 과반수: 2 / 3 etcd/raft v3.7.0 실제 네트워크가 아닌 결정적 시험
결과 용어 전체 흐름 alpha 넣기 저장 순서 WAL·snapshot 재시작 시험 범위
01 · 결과부터

이 코드가 먼저 증명하는 한 가지

입력

node 1이 명령을 먼저 받는 노드라고 가정합니다. 애플리케이션은 다음 값을 제안합니다.

node1.Propose([]byte("alpha"))

확인하는 결과

세 노드가 같은 순서로 명령을 적용합니다. 그 뒤 node 1을 닫고 node 2를 새 명령을 받는 노드로 만들면, node 2와 node 3은 이전 명령을 잃지 않고 다음 명령까지 이어갑니다.

처음: node 1·2·3 = [alpha]
이후: node 2·3 = [alpha, beta]
가장 짧은 결론: alpha를 여러 노드의 메모리에 복사한 것이 아닙니다. 합의 코어가 정한 순서에 따라 기록하고, 적용한 위치를 저장하고, 다시 열 때 그 기록을 읽어 같은 상태를 만드는 실험입니다.
중요한 범위: 이 결과는 tests/integration/raft_consensus_test.go의 메모리 FIFO 전달 시험입니다. 실제 TCP/RPC 전송, TLS, 인증을 통과했다는 뜻은 아닙니다.
02 · 용어를 네 개만

뒤의 코드를 읽는 데 필요한 약속

어려운 단어를 먼저 외울 필요는 없습니다. 아래 네 가지를 “누가 무엇을 하는가”로 기억하면 됩니다.

명령을 먼저 받는 노드(leader)

클라이언트 명령을 먼저 받고, 다른 노드에 확인을 요청하는 노드입니다. 현재 코드에서 node 1이 항상 leader라는 뜻은 아닙니다. 시험 중 선거를 거쳐 정해집니다.

과반수(quorum)

세 노드 중 두 노드입니다. 한 노드가 멈춰도 두 노드가 같은 기록을 확인하면 진행할 수 있지만, 한 노드만 남으면 새 명령을 확정할 수 없습니다.

합의 계산기(RawNode)

etcd/raft가 선거와 기록 순서를 계산하는 객체입니다. 파일에 쓰거나 메시지를 실제로 보내지는 않습니다. NaruMQ의 Node가 그 바깥 작업을 담당합니다.

이번 작업 묶음(Ready)

RawNode가 “저장할 기록, 다른 노드로 보낼 메시지, 적용할 확정 기록”을 한 번에 내놓는 값입니다. NaruMQ는 이 값을 처리한 뒤 Advance를 호출합니다.

03 · 전체 흐름

alpha가 지나가는 여섯 장소

아래 화살표는 “데이터가 다음 책임으로 이동한다”는 뜻입니다.

1 · 입력Propose애플리케이션 명령
2 · 계산RawNode기록 순서 계산
3 · 저장wal.bin먼저 파일에 기록
4 · 전달MessageDTO시험 FIFO로 전달
5 · 적용BatchDTO.Commands확정된 opaque [][]byte를 상태에 반영
6 · 복구snapshot + WAL다시 열어 상태 복원

시작점은 raft.Open이고, 실제 시험의 노드 생성은 newDeterministicCluster입니다.

04 · alpha 넣기

Propose는 “완료”가 아니라 “제안”이다

Node.Propose를 읽을 때는 네 조건만 보면 됩니다. 현재 노드가 leader인지, 명령이 비어 있지 않은지, 너무 크지 않은지, 호출자가 가진 바이트를 내부에서 복사하는지입니다. 

// internal/adapters/raft/node.go:222-243
// 설명을 위해 핵심 조건과 오류 변환만 남긴 단순화한 발췌다.
if n.raw.Status().RaftState != etcdraft.StateLeader {
    return ErrNotLeader
}
if len(data) == 0 {
    return ErrEmptyCommand
}
if len(data) > maxProposalSize {
    return ErrProposalTooLarge
}
command := bytes.Clone(data)
if err := n.raw.Propose(command); err != nil {
    if errors.Is(err, etcdraft.ErrProposalDropped) {
        return fmt.Errorf("%w: %v", ErrBackpressure, err)
    }
    return err
}
return nil

왜 leader만 받는가?

기록 순서를 여러 노드가 동시에 정하면 서로 다른 순서가 생길 수 있습니다. 그래서 제안의 시작점을 한 leader로 제한합니다.

왜 복사하는가?

호출자가 원래 배열을 바꿔도 합의 코어가 받은 명령은 바뀌지 않아야 합니다. 테스트도 alpha를 넣은 뒤 원본을 Xlpha로 바꾸는 상황을 확인합니다.

아직 무엇이 아닌가?

Propose가 성공해도 세 노드에 확정된 것은 아닙니다. 이후 Ready를 저장하고 메시지를 전달해야 CommittedEntries가 생깁니다.

05 · 가장 중요한 순서

왜 “저장 → 전달 → 적용 → 완료 표시”인가

Node.ProcessReady는 Ready를 네트워크에 바로 넘기지 않습니다. 먼저 appendReady가 WAL에 쓰고 Sync합니다. 저장 실패가 나면 노드를 실패 상태로 고정하고, 메시지를 성공 결과로 반환하지 않습니다.

RawNode.Ready()

이번에 처리할 기록 묶음을 꺼냅니다.

WAL에 기록하고 Sync

디스크에 실제로 남았다고 확인한 뒤 다음 단계로 갑니다.

peer 메시지를 MessageDTO로 복사

protobuf 바이트를 adapter 소유의 독립된 값으로 만듭니다.

확정된 명령을 [][]byte로 적용

비어 있지 않은 일반 entry의 payload만 opaque command byte 목록에 추가합니다. Adapter는 JSON이나 ownership 의미를 해석하지 않습니다.

RawNode.Advance(ready)

같은 Ready를 다시 처리하지 않았다고 계산기에 알립니다.

// 설명을 위해 핵심 순서만 줄인 의사코드
ready := n.raw.Ready()
store.appendReady(ready)       // 실패하면 여기서 중단
messages := copyPeerMessages(ready.Messages)
commands := applyCommittedEntries(ready.CommittedEntries) // [][]byte
batch := BatchDTO{Messages: messages, Commands: commands}
n.raw.Advance(ready)

Node.AppliedCommands()는 snapshot과 WAL replay를 포함해 adapter가 보존한 opaque command bytes의 독립 복사본을 반환합니다. Ownership application이 필요할 때만 이 stream을 해석하고 application sequence position을 부여합니다.

순서를 바꾸면 생기는 문제: 메시지를 먼저 보내고 프로세스가 죽으면, 다른 노드는 기록을 받았지만 보낸 노드의 디스크에는 그 기록이 없을 수 있습니다. 이 구현은 그 위험을 줄이기 위해 저장 성공 뒤에만 outbound 메시지를 만듭니다.
06 · 파일에 남는 것

WAL과 snapshot은 같은 파일이 아니다

둘 다 복구에 사용하지만 역할이 다릅니다. WAL은 최근 변화의 순서표이고, snapshot은 이미 적용한 상태를 한 번에 담은 기준점입니다.

WAL: 최근 변화의 순서표

wal.bin에는 NMQWAL01 표식 뒤에 길이와 CRC32C 검사값이 붙은 기록 묶음이 이어집니다.

NMQWAL01
[길이][CRC32C][HardState·Entry·Snapshot]
[길이][CRC32C][다음 기록]

readWAL은 파일 끝에서 잘린 기록은 마지막 정상 위치까지 자르고, 중간 기록의 검사가 틀리면 ErrCorruptWAL로 중단합니다.

snapshot: 복구 기준점

createSnapshot은 적용 위치와 Raft 설정, 애플리케이션 명령 목록을 저장합니다. 파일은 임시 이름으로 쓴 뒤 sync하고 완성 이름으로 바꿉니다.

NMQSNAP1
[길이][CRC32C][Raft snapshot]
NMQSTATE1 + [alpha, beta, ...]

최신 완성 snapshot이 손상되면 오래된 파일로 조용히 대체하지 않고 ErrCorruptSnapshot을 반환합니다.

짧은 비유: snapshot은 책갈피이고 WAL은 책갈피 뒤의 메모입니다. [alpha, beta] snapshot 뒤에 gamma WAL이 있으면, 다시 열 때 책갈피를 먼저 읽고 gamma만 이어서 적용합니다.
07 · 재시작

node 2를 닫았다가 다시 열면

raft.Open은 먼저 node ID와 세 peer ID가 맞는지 확인하고, openStableStore를 호출합니다. 이 함수는 최신 snapshot을 먼저 적용한 뒤 WAL 기록을 순서대로 읽습니다.

1. 저장 디렉터리 신원을 확인

cluster.meta의 node ID와 peer 집합이 현재 설정과 다르면 엽니다.

2. 최신 snapshot을 읽음

이미 적용한 명령과 적용 위치를 메모리 저장소에 넣습니다.

3. snapshot 이후 WAL만 재생

빠진 기록을 순서대로 적용해 명령 목록을 다시 만듭니다.

4. 같은 적용 위치에서 다시 시작

시험은 reopen 직후 CommitIndex == AppliedIndex인지 확인합니다.

처음: node 2 = [alpha]
node 2 종료
node 2 재개방
snapshot + 이후 WAL → node 2 = [alpha]
node 2 재가입 후 beta → [alpha, beta]

이 흐름은 WAL replay restores commit 시험과 snapshot plus WAL tail restores state 시험에서 확인합니다.

08 · 시험이 확인하는 것

네 가지 장애를 한 표로 읽기

통합 시험의 pump는 각 노드의 ProcessReady 결과를 FIFO 목록에 넣고, 메시지의 목적지에 Step으로 전달합니다. 실제 소켓 대신 순서를 고정했기 때문에 같은 입력을 반복해서 확인할 수 있습니다.

구현: pump · 전체 시험: TestRaftConsensusSpike

시험무슨 일을 하는가관찰 결과
leader 장애node 1이 alpha를 확정한 뒤 닫고 node 2가 선거를 시작합니다.term이 증가하고 node 2·3에 [alpha, beta]가 남습니다.
과반수 손실모든 노드 사이의 전달을 막고 gamma와 반복 제안을 시도합니다.gamma는 적용되지 않고 반복 제안은 ErrBackpressure에 도달합니다.

경계값 단위 시험

node lifecycle 시험은 잘못된 peer 설정, bootstrap, close 이후 호출을 확인합니다. message/proposal validation 시험은 leader가 아닌 노드와 잘못된 메시지를 거절하는지 확인합니다.

저장 손상 시험

WAL 충돌 suffix, 잘린 끝과 중간 손상, 손상된 최신 snapshot, Ready 순서를 별도로 확인합니다.

09 · 구현 경계

이번 결과가 의미하지 않는 것

  • 실제 peer TCP/RPC transport가 완성되었다는 뜻이 아닙니다. 현재는 in-process FIFO 시험입니다.
  • 인증, TLS, membership join/leave/change가 구현되었다는 뜻이 아닙니다.
  • MQTT QoS 1·2 durable ACK, session ownership, fencing이 이 adapter에 연결되었다는 뜻이 아닙니다.
  • disk full, 느린 follower, production 성능·가용성 기준을 통과했다는 뜻이 아닙니다.
  • ADR-0002는 Proposed 상태입니다. etcd/raft v3.7.0은 이번 spike에 사용한 버전이지 production contract 승인이 아닙니다.
정리: 이번 코드는 “세 노드 합의 계산기와 local WAL/snapshot 경계를 시험할 수 있는가”에 답합니다. “완성된 분산 MQTT 브로커인가”에는 답하지 않습니다.
