# Frontend Workflow

프로젝트의 채택된 기준을 공통 컴포넌트와 실제 화면으로 연결한다. 디자인 값과 검증 절차는 프로젝트 문서에서 관리하고 스킬에 복제하지 않는다.

## 시작점

1. [프로젝트 작업 안내](../../../docs/README.md#프로젝트-작업-안내)에서 실제 코드 지도, 컨벤션과 실행·검증 절차를 찾는다.
2. 아래 모드 표에서 필요한 [상세 절차](references/frontend-workflow.md)를 선택한다.
3. 관련 PRD·스펙, 디자인 기준, 모듈 설계와 기존 토큰·컴포넌트·호출 위치를 확인한다.

[채택·충돌 규칙](../../../docs/AGENTS.md#기준-문서-적용과-충돌-처리)에 따라 적용 범위를 확인한다.

디자인 탐색은 PRD와 화면 동작 문서(화면 스펙 또는 스펙의 화면 절)를 쓴 뒤에 시작한다. 그 문서에 화면 ID, 상태, 입력 검증, 수용 테스트가 있어야 한다. 자세한 조건은 [시작 조건](references/frontend-workflow.md#시작-조건-1단계)을 따른다.

## 요청에 맞는 모드

| 모드 | 요청 | 읽을 절과 결과 |
| --- | --- | --- |
| 디자인 탐색 | 디자인 방향·공통 스타일을 정한다. | [4절](references/frontend-workflow.md#4-디자인-탐색과-대표-화면). 동작 문서가 갖춰진 뒤 참고 디자인을 모으고 DESIGN.md를 `Accepted`로 확정한다. 채택 전 대표 화면 확인은 선택이다. |
| 구현 | 화면·컴포넌트를 만든다. | [5절](references/frontend-workflow.md#5-공통-기준과-구현). DESIGN.md가 `Accepted`가 된 뒤 화면별 HTML 시안을 만들고, 시안이 채택된 화면을 시안과 대조하며 구현한다. |
| 검토 | 디자인·UI·접근성을 점검한다. | [6절](references/frontend-workflow.md#6-검증-환경과-통과-기준). 위반 위치·확인 범위·개선안을 제시한다. 검토만 요청받았으면 구현을 바꾸지 않는다. |

## 기준과 재사용

- 화면 동작은 스펙, 시각 기준은 DESIGN.md와 토큰 원본, props와 내부 구조는 모듈 설계를 따른다.
- 기존 토큰·컴포넌트·변형을 먼저 재사용한다. 새 공통 스타일과 화면별 예외는 [5절](references/frontend-workflow.md#5-공통-기준과-구현)에 따라 반영한다.
- 기준이 없으면 [디자인 문서 작성 규칙](../../../docs/design/AGENTS.md)과 [컨벤션 작성 규칙](../../../docs/conventions/AGENTS.md)에 따라 필요한 범위만 작성한다.

## 구현과 확인

작업 순서와 단계별 산출물·넘어갈 기준은 [4절](references/frontend-workflow.md#4-디자인-탐색과-대표-화면)에서 관리한다. 전체는 동작 문서 완료, 참고 디자인 수집, DESIGN.md 확정, 화면별 HTML 시안, 구현과 대조의 5단계다. 기존 기준을 적용하는 작은 변경은 필요한 단계만 진행한다.

HTML 시안은 화면 스펙이 링크하는 시각 산출물이며 동작 기준이 아니다. 시안 검토 결과를 구현 검증의 증거로 쓰지 않는다. 구현 확인용 미리보기는 실제 컴포넌트와 공통 스타일을 재사용한다. 실행 방식은 프로젝트 프런트엔드 컨벤션을 따른다.

검증 항목·성공 조건은 [6절](references/frontend-workflow.md#6-검증-환경과-통과-기준), 결과 기록은 [7절](references/frontend-workflow.md#7-검증-증거와-완료-보고)을 따른다. 실행하지 못한 확인은 미실행으로 남긴다.

## 기록과 보고

완료 보고에는 적용 기준·범위, 재사용·추가한 토큰과 컴포넌트를 적는다. 검증 결과와 변경 이해 요약은 [루트 작업 지침](../../../AGENTS.md)을 따른다.
