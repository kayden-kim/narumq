# 디자인 기준에 따라 프런트엔드를 개발하는 방법

동작 문서를 먼저 쓰고, 참고 디자인을 모아 DESIGN.md를 확정한 뒤 화면별 HTML 시안으로 확인하고 구현한다. [프로젝트 작업 순서](../../../../AGENTS.md#작업-순서와-필수-참조)에 프런트엔드 절차를 연결한다. 실제 프로젝트의 실행 명령·검증 결과는 프로젝트 문서에서 관리한다. 이 참고 문서는 실제 앱에서 실행 검증하지 않았다.

## 1. 문서와 산출물의 역할

| 질문 | 기준 위치 | 관련 작성 규칙 |
| --- | --- | --- |
| 무엇을 왜 만드는가? | 프로젝트 PRD | [PRD 작성 규칙](../../../../docs/requirements/AGENTS.md) |
| 화면은 언제 무엇을 표시하고 어떻게 반응하는가? | 관련 스펙의 화면 절 또는 별도 화면 스펙 | [스펙 작성 규칙](../../../../docs/specs/AGENTS.md) |
| 화면의 시각 구성은 어떻게 보이는가? | 화면 스펙이 링크하는 HTML 시안(`docs/design/mockups/`). 동작 기준은 아니다. | [디자인 문서 작성 규칙](../../../../docs/design/AGENTS.md) |
| 어떤 공통 시각 기준을 적용하는가? | 프로젝트 디자인 시스템(`docs/design/DESIGN.md`) | [디자인 문서 작성 규칙](../../../../docs/design/AGENTS.md) |
| 코드는 어떤 방식으로 스타일을 적용하는가? | 프로젝트 프런트엔드 컨벤션 | [컨벤션 작성 규칙](../../../../docs/conventions/AGENTS.md) |
| 컴포넌트는 어디에 있고 어떤 책임을 맡는가? | 코드 지도·모듈 설계 | [아키텍처 문서 작성 규칙](../../../../docs/architectures/AGENTS.md) |
| 실제 변형과 상태는 어떻게 보이는가? | 실제 컴포넌트를 사용하는 미리보기 페이지 또는 기존 카탈로그 | 프로젝트가 채택한 실행 위치와 도구 |
| 에이전트는 어떻게 작업을 진행하는가? | 프로젝트 전용 스킬 | [frontend-workflow](../SKILL.md) |

화면 문서의 분리 기준은 [스펙 규칙](../../../../docs/specs/AGENTS.md)을 따른다. Figma 같은 외부 시안은 원본 링크와 버전으로 연결한다. HTML 시안은 화면 스펙이 링크한다.

## 2. 준비와 적용 범위

- [ ] 관련 PRD와 화면 동작의 기준 문서를 찾았다.
- [ ] 코드 지도에서 기존 스타일·공통 컴포넌트·호출 위치를 확인했다.
- [ ] 기존 디자인 시스템, 토큰 원본과 자산을 확인했다.
- [ ] 프레임워크·라이브러리·검증 명령은 실제 설정에서 확인했다.
- [ ] 지원할 화면 크기·테마·접근성·성능 기준을 찾았다.
- [ ] 작업 범위에 영향을 주는 미결정 사항을 확인했다.

채택 여부와 미결정 사항은 [문서 적용 규칙](../../../../docs/AGENTS.md#기준-문서-적용과-충돌-처리)을 따른다.

## 3. 작업 기준 연결

1. 작업 범위에 적용할 기존 PRD·스펙·디자인 기준과 프런트엔드 컨벤션을 연결한다.
2. 필요한 기준이 없으면 해당 디렉터리의 `AGENTS.md`에 따라 작성한다.
3. 토큰의 유일한 원본을 프로젝트 디자인 기준에서 확인한다.
4. [프로젝트 작업 안내](../../../../docs/README.md#프로젝트-작업-안내)에 실제 기준 문서와 검증 절차를 연결한다.

루트 `DESIGN.md`를 요구하는 도구가 있으면 한 곳만 원본으로 정한다. 다른 위치의 파일은 원본 링크 또는 생성된 표현으로 관리한다. 도구의 형식을 맞추려고 두 문서를 각각 수정하지 않는다.

토큰 원본은 DESIGN.md에서 지정한다. 참조·생성 관계와 생성 대상 밖의 규칙은 프런트엔드 컨벤션에서 관리한다.

## 4. 디자인 탐색과 대표 화면

프런트엔드 작업의 전체 순서는 아래 5단계다. 4절은 1~3단계, 5절은 4~5단계를 다룬다.

| 단계 | 할 일 | 산출물 | 다음 단계로 넘어갈 기준 |
| --- | --- | --- | --- |
| 1. 동작 문서 완료 | PRD와 화면 스펙을 쓴다. 화면 스펙에 화면 ID, 상태, 입력 검증, 수용 테스트를 쓴다. | PRD, 화면 스펙 또는 스펙의 화면 절 | 아래 시작 조건을 모두 만족한다. |
| 2. 참고 디자인 수집 | 대상 사용자와 주요 작업에 맞는 참고 디자인을 모은다. | DESIGN.md "디자인 방향"의 참고 자료 | 자료마다 링크, 채택할 요소, 채택하지 않을 요소를 구분했다. |
| 3. DESIGN.md 확정 | 참고 자료를 근거로 토큰과 컴포넌트 기준을 `Draft`로 쓰고, 사용자의 채택을 받는다. | `docs/design/DESIGN.md` | 사용자가 채택했고 DESIGN.md가 `Accepted`이다. |
| 4. 화면별 HTML 시안 | DESIGN.md가 `Accepted`가 된 뒤, 화면 스펙마다 HTML 시안을 만든다. | 화면 스펙별 HTML 시안 | 모든 화면 ID와 상태가 시안에 있고 사용자가 시안을 채택했다. |
| 5. 구현과 대조 | 시안이 채택된 화면부터 구현하고 시안과 대조한다. | 구현, 검증 증거 | 차이를 해소했고 검증 기준을 통과했다. |

채택된 디자인 방향이 있으면 필요한 단계부터 진행한다. 기존 DESIGN.md가 `Accepted`이면 새 후보를 만들지 않는다. 사용자 요청으로 변경할 부분만 탐색한다.

### 시작 조건 (1단계)

다음 조건을 모두 만족해야 디자인 탐색을 시작한다.

- PRD가 있고 요구사항 ID가 있다.
- 화면 스펙 또는 스펙의 화면 절이 있다.
- 그 문서에 화면 ID, 화면 상태, 입력 검증, 수용 테스트가 있다.

조건이 부족하면 [스펙 규칙](../../../../docs/specs/AGENTS.md)에 따라 먼저 쓴다. 시안을 만들려고 상태나 시나리오를 임의로 추가하지 않는다.

### 참고 디자인 수집 (2단계)

참고 자료는 DESIGN.md의 "참고 자료" 항목에 기록한다. 별도 참고 자료 폴더를 만들지 않는다.

- 항목마다 링크, 채택할 요소, 채택하지 않을 요소를 쓴다.
- 디자인 방향이 미정이면 근거가 있는 후보를 비교한다.

### DESIGN.md 확정 (3단계)

1. 선택한 방향의 채택 근거와 적용 범위를 DESIGN.md에 쓴다.
2. 토큰과 컴포넌트 기준을 `Draft`로 쓴다.
3. 사용자가 DESIGN.md를 채택하면 상태를 `Accepted`로 바꾼다. 채택 근거를 남긴다.

DESIGN.md가 `Accepted`가 되기 전에는 화면별 HTML 시안과 구현을 시작하지 않는다.

채택한 뒤에는 참고 자료를 과거 자료로 본다. DESIGN.md에는 채택 이유를 설명하는 요소만 남기고 나머지는 지운다. 기준은 [문서 작성 원칙](../../../../docs/AGENTS.md#작성-원칙)의 현재 상태 규칙을 따른다.

#### 대표 화면 확인 (3단계, 선택)

채택 전에 초안 토큰을 검증하려면 대표 화면 하나를 초안 토큰으로 그려 볼 수 있다. 이 시안은 탐색 결과물이다. 4단계의 채택된 시안이 아니다.

대표 화면은 첫 구현 범위에 맞춰 선택한다. 폼·표·긴 제목처럼 공통 스타일의 약점을 드러내는 화면을 권장한다. 실제 요구사항에 있는 정상·빈 결과·오류·로딩 상태를 포함한다. 지원하지 않는 상태나 화면을 검증 목적으로 제품에 추가하지 않는다.

1. 대표 화면의 화면 스펙을 연결하고, 검토할 시나리오를 DESIGN.md의 "대표 화면"에 기록한다.
2. 화면 스펙의 "화면 상태" 표에 있는 모든 화면 ID와 상태를 HTML 시안으로 만든다. 위치와 작성 규칙은 [디자인 문서 작성 규칙](../../../../docs/design/AGENTS.md#html-시안)을 따른다.
3. 시안은 DESIGN.md 초안의 토큰만 사용한다. 토큰이 부족하면 시안에 임의 값을 쓰지 말고 DESIGN.md를 고친 뒤 시안을 다시 만든다.
4. 브라우저에서 지원하는 화면 폭마다 시안을 열고 모든 상태를 확인한다. 긴 한글과 빈 값처럼 스펙이 정한 경계 콘텐츠도 확인한다.
5. 시안에서 드러난 기준 문제는 DESIGN.md에 반영한다.

DESIGN.md가 `Accepted`가 되면 이 화면의 시안을 채택된 토큰으로 다시 확인하고 필요하면 고친다. 그다음 4단계에서 다른 화면과 같은 절차로 사용자의 채택을 받는다.

## 5. 공통 기준과 구현

### 화면별 HTML 시안 (4단계)

DESIGN.md가 `Accepted`가 된 뒤에 시작한다.

1. 화면 스펙마다 HTML 시안을 하나씩 만든다. 위치와 작성 규칙은 [디자인 문서 작성 규칙](../../../../docs/design/AGENTS.md#html-시안)을 따른다.
2. 화면 스펙의 "화면 상태" 표에 있는 모든 화면 ID와 상태를 시안에 넣는다.
3. 시안은 채택된 토큰과 컴포넌트만 사용한다.
4. 공통으로 필요한 값이 부족하면 DESIGN.md에 사용 조건과 함께 먼저 추가한다.
5. 한 화면에만 필요한 값은 DESIGN.md의 예외 표에 범위·이유·재검토 조건을 남긴다.
6. 브라우저에서 지원하는 화면 폭마다 시안을 열고 모든 상태와 스펙이 정한 경계 콘텐츠를 확인한다.
7. 화면 스펙의 헤더 표에 시안 링크를 쓴다. 시안을 추가·이름 변경·삭제하면 [디자인 목록](../../../../docs/design/README.md)도 함께 고친다.
8. 시안과 스펙 문장이 다르면 스펙 문장을 따른다. 시안을 고친다. 스펙이 틀렸으면 스펙을 먼저 고친다.
9. 사용자가 시안을 채택한다.

화면의 구현은 그 화면의 시안을 사용자가 채택한 뒤에 시작한다.

### 구현과 대조 (5단계)

1. 구현할 화면의 시안이 채택됐는지 확인한다.
2. 화면의 구성요소를 기존 토큰·컴포넌트·변형에 대응시킨다.
3. 새 컴포넌트가 필요하면 책임과 API를 관련 모듈 설계에 정리한다.
4. 채택된 범위의 토큰과 공통 컴포넌트를 구현한다.
5. 컴포넌트의 필요한 변형과 상태를 미리보기 페이지 또는 기존 카탈로그에서 재현한다.
6. 화면을 실제 콘텐츠와 스펙 상태로 구현한다.
7. 구현 화면을 채택된 시안과 같은 화면 폭·같은 상태로 대조한다.
8. 차이의 원인을 확인한다. 구현 오류는 시안과 기준에 맞춘다.
9. 기준 변경이 필요하면 채택 근거를 확인한 뒤 DESIGN.md·시안·구현을 함께 갱신한다.

여러 화면은 같은 토큰과 컴포넌트로 하나씩 구현하고 각 시안과 대조한다.

변경 때마다 전체 절차를 처음부터 반복하지 않는다. 기존 기준과 컴포넌트로 해결할 수 있으면 해당 범위만 구현·검증한다. 새 공통 스타일이면 변형을 추가한다. 화면별 예외이면 DESIGN.md의 예외 표에 범위·이유·재검토 조건을 남긴다.

시안 검토는 구현 검증의 증거가 아니다. 구현 검증은 실제 컴포넌트와 공통 스타일로 수행한다.

### 컴포넌트 미리보기 준비

미리보기 방식과 완료 조건은 프로젝트 프런트엔드 컨벤션을 따른다. 기존 미리보기나 카탈로그가 있으면 재사용한다.

1. 실제 컴포넌트를 확인할 미리보기의 코드 경로와 실행 위치를 기록한다.
2. 앱의 컴포넌트와 공통 스타일을 미리보기에 연결한다.
3. 필요한 실행 문맥과 예시 데이터를 연결한다.
4. 디자인 기준과 관련 스펙에 필요한 상태를 재현한다.
5. 지원하는 테마와 화면 크기에서 렌더링을 확인한다.
6. 필요한 사용자 행동과 키보드·포커스 흐름을 확인한다.
7. 검증 방법과 결과를 관련 기준 문서에 연결한다.

실제 버튼·입력을 확인한 뒤 필드 묶음·폼으로 확장한다. 시안 검토와 구현 검증의 결과는 구분한다.

### 디자인 문서 검사

채택한 문서·토큰 형식과 검사 도구를 확인한다. 자리표시자가 남은 템플릿을 실제 디자인 기준으로 판정하지 않는다.

문서 구조·토큰 참조·생성 산출물의 일치 여부와 필요한 대비 기준을 확인한다. 오류와 경고의 처리 기준을 구분한다. 종료 코드만으로 통과를 판단하지 않고 적용 기준에 해당하는 검사 결과도 확인한다. 실제 화면의 접근성은 별도로 검사한다.

### 시각 검토

기준 이미지는 채택된 디자인을 구현한 결과인지 먼저 검토한다. 스크린샷 회귀 검사는 그 뒤에 기준 이미지와 현재 렌더링을 비교한다. OS·브라우저·폰트·데이터·시간·애니메이션 등 결과에 영향을 주는 조건을 고정한다. 차이가 나면 원인을 확인한 뒤 기준을 바꾼다. 현재 화면으로 기준 이미지를 무조건 갱신하지 않는다.

## 7. 검증 증거와 완료 보고

결과와 증거는 [검증 기록 규칙](../../../../docs/AGENTS.md#검증-기록)을 따른다. 화면 동작의 증거는 테스트 메타 정보 기반 커버리지·결과 보고서를 연결한다. 시각·컨벤션 검사는 검증 how-to에서 관리한다.

시각 검토와 컨벤션 검사는 다음 형식으로 별도 기록할 수 있다. 관련 스펙 시나리오가 있으면 함께 연결한다.

| 확인 대상 | 기준 문서·범위 | 환경·명령·방법 | 실제 결과 | 실행·검토 증거 |
| --- | --- | --- | --- | --- |
| {{토큰·컴포넌트·화면}} | {{버전·변경 범위·시나리오}} | {{실제 실행 조건}} | {{통과·실패·미실행과 관찰 결과}} | {{CI 실행·로컬 실행·스크린샷·검토 기록}} |

완료 보고는 [루트 작업 지침](../../../../AGENTS.md#작업-순서와-필수-참조)을 따른다.

## 8. 중단과 복구

- 근거 없는 디자인 결정이나 문서 충돌이 구현에 영향을 주면 해당 범위만 멈춘다.
- 토큰 생성 결과가 기준과 다르면 화면 확장 전에 원본·도구 버전·생성 설정을 확인한다.
- 필수 검증이 실패하면 원인과 영향을 기록한다.
- 되돌릴 때는 해당 변경의 토큰 원본과 생성 산출물·컴포넌트·문서를 함께 맞춘다.
- 기존 사용자 변경과 무관한 파일을 함께 되돌리지 않는다.

결정이 필요하면 충돌 내용·선택·영향을 사용자나 프로젝트의 결정 책임자에게 전달한다. 로그와 스크린샷에는 비밀 값이나 실제 개인정보를 남기지 않는다.
