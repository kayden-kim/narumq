# 디자인 기준에 따라 프런트엔드를 개발하는 방법

디자인 방향을 정하고 대표 화면에서 확인한 뒤 확장한다. [프로젝트 작업 순서](../../../../AGENTS.md#작업-순서와-필수-참조)에 프런트엔드 절차를 연결한다. 실제 프로젝트의 실행 명령·검증 결과는 프로젝트 문서에서 관리한다. 이 참고 문서는 실제 앱에서 실행 검증하지 않았다.

## 1. 문서와 산출물의 역할

| 질문 | 기준 위치 | 관련 작성 규칙 |
| --- | --- | --- |
| 무엇을 왜 만드는가? | 프로젝트 PRD | [PRD 작성 규칙](../../../../docs/requirements/AGENTS.md) |
| 화면은 언제 무엇을 표시하고 어떻게 반응하는가? | 관련 스펙의 화면 절 또는 별도 화면 스펙 | [스펙 작성 규칙](../../../../docs/specs/AGENTS.md) |

| 코드는 어떤 방식으로 스타일을 적용하는가? | 프로젝트 프런트엔드 컨벤션 | [컨벤션 작성 규칙](../../../../docs/conventions/AGENTS.md) |

| 실제 변형과 상태는 어떻게 보이는가? | 실제 컴포넌트를 사용하는 미리보기 페이지 또는 기존 카탈로그 | 프로젝트가 채택한 실행 위치와 도구 |
| 에이전트는 어떻게 작업을 진행하는가? | 프로젝트 전용 스킬 | [frontend-workflow](../SKILL.md) |

화면 문서의 분리 기준은 [스펙 규칙](../../../../docs/specs/AGENTS.md)을 따른다. 시안은 원본 링크와 버전으로 연결한다.

## 2. 준비와 적용 범위

- [ ] 관련 PRD와 화면 동작의 기준 문서를 찾았다.
- [ ] 코드 지도에서 기존 스타일·공통 컴포넌트·호출 위치를 확인했다.
- [ ] 기존 디자인 시스템, 토큰 원본과 자산을 확인했다.
- [ ] 프레임워크·라이브러리·검증 명령은 실제 설정에서 확인했다.
- [ ] 지원할 화면 크기·테마·접근성·성능 기준을 찾았다.
- [ ] 작업 범위에 영향을 주는 미결정 사항을 확인했다.

채택 여부와 미결정 사항은 [문서 적용 규칙](../../../../docs/AGENTS.md#기준-문서-적용과-충돌-처리)을 따른다.

## 3. 작업 기준 연결

1. 작업 범위에 적용할 기존 PRD·스펙·디자인 기준과 프런트엔드 컨벤션을 연결한다.
2. 필요한 기준이 없으면 해당 디렉터리의 `AGENTS.md`에 따라 작성한다.
3. 토큰의 유일한 원본을 프로젝트 디자인 기준에서 확인한다.
4. [프로젝트 작업 안내](../../../../docs/README.md#프로젝트-작업-안내)에 실제 기준 문서와 검증 절차를 연결한다.

루트 `DESIGN.md`를 요구하는 도구가 있으면 한 곳만 원본으로 정한다. 다른 위치의 파일은 원본 링크 또는 생성된 표현으로 관리한다. 도구의 형식을 맞추려고 두 문서를 각각 수정하지 않는다.

토큰 원본은 DESIGN.md에서 지정한다. 참조·생성 관계와 생성 대상 밖의 규칙은 프런트엔드 컨벤션에서 관리한다.

## 4. 디자인 탐색과 대표 화면

기존에 채택된 디자인 방향이 있으면 새 후보를 만들 필요가 없다. 사용자 요청으로 변경할 부분만 탐색한다.

1. 제품의 대상 사용자와 주요 작업을 디자인 방향 초안에 기록한다.
2. 디자인 방향이 미정이면 근거가 있는 후보를 작성한다.
3. 후보를 비교할 대표 화면을 선택한다.
4. 대표 화면에서 검토할 스펙 시나리오를 연결한다.
5. 선택한 방향의 채택 근거와 적용 범위를 DESIGN.md에 기록한다.

대표 화면은 첫 구현 범위에 맞춰 선택한다. 폼·표·긴 제목처럼 공통 스타일의 약점을 드러낼 수 있는 화면을 권장한다. 실제 요구사항에 있는 정상·빈 결과·오류·로딩 상태를 포함한다. 지원하지 않는 상태나 화면을 검증 목적으로 제품에 추가하지 않는다.

## 5. 공통 기준과 구현

1. 대표 화면의 구성요소를 기존 토큰·컴포넌트·변형에 대응시킨다.
2. 부족한 공통 시각 기준을 DESIGN.md에 정리한다.
3. 새 컴포넌트가 필요하면 책임과 API를 관련 모듈 설계에 정리한다.
4. 근거가 채택된 범위의 토큰과 공통 컴포넌트를 구현한다.
5. 컴포넌트의 필요한 변형과 상태를 미리보기 페이지 또는 기존 카탈로그에서 재현한다.
6. 대표 화면을 실제 콘텐츠와 스펙 상태로 구현한다.
7. 구현 화면을 기준 시안과 대조한다.
8. 차이의 원인을 확인한다. 구현 오류는 기존 기준에 맞춘다.
9. 기준 변경이 필요하면 채택 근거를 확인한 뒤 문서와 구현을 함께 갱신한다.
10. 나머지 화면을 같은 토큰과 컴포넌트로 구현한다.

변경 때마다 전체 절차를 처음부터 반복하지 않는다. 기존 기준과 컴포넌트로 해결할 수 있으면 해당 범위만 구현·검증한다. 새 공통 스타일이면 변형을 추가한다. 화면별 예외이면 DESIGN.md의 예외 표에 범위·이유·재검토 조건을 남긴다.

### 컴포넌트 미리보기 준비

미리보기 방식과 완료 조건은 프로젝트 프런트엔드 컨벤션을 따른다. 기존 미리보기나 카탈로그가 있으면 재사용한다.

1. 실제 컴포넌트를 확인할 미리보기의 코드 경로와 실행 위치를 기록한다.
2. 앱의 컴포넌트와 공통 스타일을 미리보기에 연결한다.
3. 필요한 실행 문맥과 예시 데이터를 연결한다.
4. 디자인 기준과 관련 스펙에 필요한 상태를 재현한다.
5. 지원하는 테마와 화면 크기에서 렌더링을 확인한다.
6. 필요한 사용자 행동과 키보드·포커스 흐름을 확인한다.
7. 검증 방법과 결과를 관련 기준 문서에 연결한다.

실제 버튼·입력을 확인한 뒤 필드 묶음·폼으로 확장한다. 시안 검토와 구현 검증의 결과는 구분한다.

### 디자인 문서 검사

채택한 문서·토큰 형식과 검사 도구를 확인한다. 자리표시자가 남은 템플릿을 실제 디자인 기준으로 판정하지 않는다.

문서 구조·토큰 참조·생성 산출물의 일치 여부와 필요한 대비 기준을 확인한다. 오류와 경고의 처리 기준을 구분한다. 종료 코드만으로 통과를 판단하지 않고 적용 기준에 해당하는 검사 결과도 확인한다. 실제 화면의 접근성은 별도로 검사한다.

### 시각 검토

기준 이미지는 채택된 디자인을 구현한 결과인지 먼저 검토한다. 스크린샷 회귀 검사는 그 뒤에 기준 이미지와 현재 렌더링을 비교한다. OS·브라우저·폰트·데이터·시간·애니메이션 등 결과에 영향을 주는 조건을 고정한다. 차이가 나면 원인을 확인한 뒤 기준을 바꾼다. 현재 화면으로 기준 이미지를 무조건 갱신하지 않는다.

## 7. 검증 증거와 완료 보고

결과와 증거는 [검증 기록 규칙](../../../../docs/AGENTS.md#검증-기록)을 따른다. 화면 동작은 스펙의 수용 시험 표에서, 시각·컨벤션 검사는 검증 how-to에서 관리한다.

시각 검토와 컨벤션 검사는 다음 형식으로 별도 기록할 수 있다. 관련 스펙 시나리오가 있으면 함께 연결한다.

| 확인 대상 | 기준 문서·범위 | 환경·명령·방법 | 실제 결과 | 실행·검토 증거 |
| --- | --- | --- | --- | --- |
| {{토큰·컴포넌트·화면}} | {{버전·변경 범위·시나리오}} | {{실제 실행 조건}} | {{통과·실패·미실행과 관찰 결과}} | {{CI 실행·로컬 실행·스크린샷·검토 기록}} |

완료 보고는 [루트 작업 지침](../../../../AGENTS.md#작업-순서와-필수-참조)을 따른다.

## 8. 중단과 복구

- 근거 없는 디자인 결정이나 문서 충돌이 구현에 영향을 주면 해당 범위만 멈춘다.
- 토큰 생성 결과가 기준과 다르면 화면 확장 전에 원본·도구 버전·생성 설정을 확인한다.
- 필수 검증이 실패하면 원인과 영향을 기록한다.
- 되돌릴 때는 해당 변경의 토큰 원본과 생성 산출물·컴포넌트·문서를 함께 맞춘다.
- 기존 사용자 변경과 무관한 파일을 함께 되돌리지 않는다.

결정이 필요하면 충돌 내용·선택·영향을 사용자나 프로젝트의 결정 책임자에게 전달한다. 로그와 스크린샷에는 비밀 값이나 실제 개인정보를 남기지 않는다.
