# Explain

결과물이 해결하는 문제와 주요 결정의 이유를 이해하고, 실제 코드에서 입력이 결과가 되는 흐름을 따라갈 수 있게 설명한다. 쉬운 표현을 쓰되 중요한 세부사항은 남긴다.

## 범위와 근거

- 사용자가 지정한 기능·파일·변경을 중심으로 설명한다. 대상이 분명하면 묻지 않고, 불명확할 때만 필요한 정보를 요청한다.
- 저장소 지침, 코드 지도·모듈 설계, 관련 PRD·스펙과 구현·호출 지점·자료 구조·시험을 확인한다. 설명 대상의 범위만 읽는다. 코드와 문서가 다르면 차이를 밝힌다.
- 업무 용어는 [용어집 규칙](../../../docs/AGENTS.md#용어집-위치)에 따라 확인한다.
- 문서의 의도, 코드에서 확인한 동작, 시험이 확인한 조건을 구분한다. 시험 파일을 읽은 사실을 시험 실행이나 전체 검증으로 표현하지 않는다.
- 설계 이유는 문서·주석·변경 기록 등의 근거와 연결한다. 근거 없는 이유는 코드의 효과나 가능한 해석으로 표시하고 확정된 의도로 단정하지 않는다.
- 보지 못한 파일·구조·구현을 만들지 않는다. 코드에 접근할 수 없으면 범위를 밝히며, 설명 요청만으로 코드를 수정하지 않는다.

## 이해의 순서

질문의 크기에 맞춰 항목을 합치거나 줄이되, 다음 흐름을 유지한다.

1. 결과와 문제: 해결한 문제와 사용자 경험을 설명한다. 대표 입력과 기대 결과를 하나 든다.
2. 배경지식: 필요한 업무 규칙·기술 개념을 현재 문제와 연결한다. 확인한 참고 자료가 도움되면 링크와 읽을 부분을 제시한다.
3. 전체 구조: 시작점부터 결과까지 파일의 책임과 호출·데이터 전달 관계를 연결한다.
4. 결정 이유: 조건이 선택으로 이어진 근거를 설명한다. 필요하면 대안·장점·제약을 비교한다.
5. 실제 흐름: 같은 입력을 함수에 대입해 조건·값·상태·결과 사용처를 호출 순서로 추적한다.
6. 세부 조건: 경계값·실패 처리·제약·한계를 설명한다. 필요하면 다시 볼 코드 위치를 연결한다.

각 설명이 다음 설명의 바탕이 되게 하고, 개요·개념·코드에서 같은 예시와 이름을 이어 쓴다.

## 쉬운 기술 글쓰기

[루트 글쓰기 규칙](../../../AGENTS.md#쉬운-한국어-글쓰기)을 따른다. 답변 언어와 관계없이 ASD-STE100의 명료성 원칙을 활용한다. 사용자가 요청한 언어를 유지한다.

문장은 짧게 쓰고, 한 문장에는 한 가지 핵심만 담는다. 모호한 표현을 피하고 능동태를 우선 쓴다. 쉬운 표현을 위해 사실·조건·인과관계나 필요한 설명을 생략하지 않는다.

짧은 문장 사이에도 개념·결정 이유·코드 흐름의 연결 관계를 남긴다.

## 생소하거나 어려운 용어 설명

- 독자의 배경지식을 기준으로 낯설거나 오해하기 쉬운 용어를 찾는다. 작성자에게 익숙하다는 이유로 설명을 생략하지 않는다.
- 용어가 처음 필요한 지점에서 정식 이름을 유지하고, 쉬운 뜻과 현재 기능에서 맡는 역할을 설명한다. 코드·문서의 실제 이름을 다른 말로 바꾸지 않는다.
- 약어는 처음 나올 때 풀어 쓴 이름과 약어를 함께 제시한다. 프로젝트 용어집이 있으면 그 정의와 표기를 따른다.
- 비슷한 용어가 함께 나오면 의미의 차이와 적용 범위를 설명한다. 핵심 흐름과 관계없는 배경이나 용어 목록은 덧붙이지 않는다.
- 같은 용어는 뒤에서도 같은 이름과 뜻으로 사용한다. 이미 설명한 내용은 불필요하게 반복하지 않는다.

## 코드와 구조

- 핵심 로직을 실제 코드에서 발췌해 언어가 지정된 블록으로 보여주고, 파일 경로와 가능한 경우 줄 번호를 연결한다.
- 코드 앞에는 문제와 읽을 관점을 쓴다. 코드 뒤에는 조건·계산·상태 변화가 개념과 어떻게 연결되는지 쓴다. 한 조각은 하나의 판단이나 변환만 담는다.
- 조건·반환값·예외를 생략하지 않는다. 생략한 부분은 표시하고, 이름이나 흐름을 바꾼 예시는 단순화한 예시 또는 의사코드라고 밝힌다.
- 값의 출처·형태·단위·범위와 반환값의 다음 사용처를 설명한다. 저장·화면 갱신·외부 요청 같은 함수 밖의 변화도 연결한다.
- 모듈·패키지의 책임과 의존 방향은 실제 호출·데이터 전달 관계로 확인한다. 패턴 이름은 역할을 설명한 뒤 쓴다. 일부 코드로 전체 패턴을 단정하지 않는다.
- 의존성 주입(DI)이 있으면 주입받는 쪽, 제공하는 쪽, 등록 위치, 인터페이스와 구현의 관계를 설명한다. `import` 관계와 실행 중 주입을 구분하고 확인하지 못한 연결은 추정으로 표시한다.
- 관련된 빈 값·경계값·순서·중복 요청·동시 실행·실패 시 되돌림·권한·자원 정리와 처리되지 않는 경우를 설명한다. 개선 제안은 현재 동작과 구분한다.
- 비유를 쓰면 각 부분이 실제 구성요소의 무엇에 해당하는지 밝힌다. 비유가 맞지 않거나 오해를 부를 수 있는 차이도 설명한다.
- 프로그래밍 언어 문법과 자료 구조는 핵심 흐름을 이해하는 데 필요한 만큼만 설명한다. 주변 내용을 모두 풀이해 핵심 동작을 가리지 않는다.

## 도식

- 구성요소 관계, 호출·응답 순서, 상태 변화, 분기가 글만으로 복잡하면 Mermaid·텍스트 그림·표를 사용한다. 입력 변화 탐색에 실질적으로 도움이 되면 상호작용 가능한 시각 자료도 고려한다.
- 모듈 경계와 의존 방향, DI의 등록·제공·사용 관계가 여러 파일에 흩어져 있으면 구조도나 흐름도를 만든다. 화살표가 호출, 컴파일 시 의존, 실행 중 주입 중 무엇을 뜻하는지 표시한다.
- 도식의 이름은 실제 코드와 맞추고, 현재 구현과 의도한 설계를 구분한다. 한 그림에는 하나의 핵심 관계만 담고, 큰 관계는 전체 구조와 세부 흐름으로 나눈다.

## 전달 전 점검

- 독자가 무엇을 왜 만들었는지, 필요한 개념을 이해했는지, 실제 입력이 결과가 되는 과정을 따라갈 수 있는지 확인한다.
- 핵심 코드와 파일·모듈·의존 관계가 연결되고, 중요한 예외·제약·한계와 사실·추정의 구분이 남아 있는지 확인한다.
- 반복과 불필요한 용어는 줄이되 이해에 필요한 세부사항은 남긴다. 이 점검 목록을 답변에 그대로 출력하지 않는다.
