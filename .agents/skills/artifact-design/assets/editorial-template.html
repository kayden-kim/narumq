시각 해설 / 요청과 응답의 관계

한 요청이
기록이 되기까지

보내는 일, 기다리는 일, 남기는 일은 서로 다릅니다. 하나의 요청을 따라가며, 대기열과 기록의 경계가 응답의 뜻을 어떻게 바꾸는지 살펴봅니다.

01 / 대기하는 공간

도착했다고 해서
끝난 것은 아닙니다.

대기열은 도착한 요청을 처리할 차례까지 보관하는 공간입니다. 이 예시에서는 요청이 들어온 순서대로 다음 처리 위치로 이동합니다.

하지만 대기열에 들어갔다는 사실만으로 기록이 남았다고 말할 수는 없습니다. 그림을 전체, 처리 위치, 기록의 세부로 나누면 이 차이가 보입니다.

READING NOTE

도착과 완료 사이에는
서로 다른 상태가 있습니다.

02 / 두 가지 경계

잠시 맡기는 일과
남겨 두는 일.

대기열은 처리할 차례를, 기록은 남긴 결과를 설명합니다. 두 장면을 나란히 놓으면 같은 요청에도 서로 다른 질문을 해야 한다는 점이 드러납니다.

ARRIVAL / 도착

다음 차례를
기다리는 공간.

여기서 확인하는 것은 요청을 받았는지입니다. 아직 기록 완료를 뜻하지 않습니다.

요청의 다음 단계 보기 →
요청 수신≠기록 완료

RECORD / 기록

결과가 남는
다른 경계.

여기서 확인하는 것은 기록을 남겼는지입니다. 이 모형에서는 그 결과에 따라 응답이 달라집니다.

응답의 차이 확인하기 →
기록 완료→성공 응답

그림 3. 두 색상 패널은 상태의 경계를 비교합니다. 화살표와 관계 기호는 요청 수신, 기록 완료, 성공 응답 사이의 뜻을 표시하며 실제 저장 구조를 나타내지 않습니다.

03 / 동작을 따라 읽기

응답은 무엇을
확인한 뒤 돌아올까요?

이 모형은 기록 결과를 확인한 뒤 응답합니다. 정상 흐름과 기록 실패를 선택해, 같은 요청이 어떻게 다른 결과로 끝나는지 살펴보세요.

직접 재생하거나 이전·다음으로 한 단계씩 확인할 수 있습니다.

0 / 요청 전

요청자는 아직 요청을 보내지 않았습니다.

04 / 다시 전체로

완료라는 말에
경계를 적습니다.

요청을 받았는지, 기록이 남았는지, 응답이 돌아왔는지는 다른 질문입니다. 실제 시스템을 설명할 때도 무엇을 확인한 상태인지 분명히 적어야 합니다.

여기서는 단순한 관계만 다뤘습니다. 실제 서비스의 재시도, 장애 복구와 저장 보장은 해당 프로젝트의 스펙과 구현에서 확인해야 합니다.
